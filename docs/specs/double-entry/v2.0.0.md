## 1. Мотивация и цель

v1.0.0 устранила захардкоженный план счетов из движка (R0.1). Относительно налоговой модели (taxation v1.0.0, разделы 7–8) остаются три пробела:

- налог, рассчитанный по событию и не удержанный на месте, не имеет учетного представления: обязательства по налогу в ledger нет, а вывод средств не удерживает налог;
- позиция хранится агрегатами (`carryingAmount`, `purchasedAccrued`, `faceAmount`, `quantity`) без лотов: налоговая себестоимость по FIFO не выражается;
- нет read view денежных средств, доступных для трат, за вычетом обязательства по налогу.

Цель (**R0.1**, без изменений): движок двойной записи не содержит словаря счетов; план счетов — данные, поставляемые composition root при открытии ledger и замороженные в его состоянии на весь срок жизни.

Новые цели v2.0.0:

- **R0.5** — учет отложенного налога (`TAX_LIABILITY`, `TAX_DEFERRED_OFFSET`), вывода с удержанием и закрытия обязательства (годовой расчет, досрочное закрытие ИИС-3) в ledger при явно переданных налоговых суммах (taxation R7.1–R7.5, R7.7; AD-10, AD-11, AD-15).
- **R0.6** — позиция хранит упорядоченный список лотов FIFO; продажа и амортизация списывают стоимость по лотам (taxation R8.1–R8.4, R8.7; AD-12).
- **R0.7** — read view `availableCashBalances()` = CASH − TAX_LIABILITY по валюте; лимит вывода не меняется (taxation R7.2–R7.3; AD-13).

Граница scope (AD-6 сохраняется): таксономия операций `OperationKind` остается enum-контрактом bond-операций, включая новые налоговые виды; диспетчеризация `Ledger.apply` по видам операций — enum-based (N6). Задача — учет налога и лотов, а не декодирование таксономии операций в данные.

## 2. Термины

- **Движок** — универсальные части `core.ledger`: `Posting`, `Account`, `Ledger`, `LedgerState`, `Position`, `Lot`, `LedgerChart`.
- **План счетов (chart)** — `LedgerChart`: множество известных кодов счетов, роли и скалярные привязки для движка.
- **Код счета** — `AccountCode`: value-тип идентичности вида счета.
- **Bond-слой** — `BondOperations`, `BondAccountingPolicy`: эмиттеры словаря и правил проводок.
- **Adjustment** — append-only корректировка удержания (`TAX_CORRECTION`, `TAX_REFUND`), postings которой связаны с исходной операцией через `Posting.adjustsOperation()`.
- **Роль `liability`** — скалярная роль chart для счета налогового обязательства (R5.2, R5.11).
- **Привязка `deferredOffset`** — скалярная привязка chart для контрсчета налогового обязательства; на балансы не влияет, используется только для проверки формы налоговых проводок (R5.11, R9.9).
- **Обязательство по налогу L** — величина счета роли `liability`: L = −(знаковый баланс счета); инвариант L ≥ 0 (R9.8, AD-19).
- **Лот** — часть позиции одной покупки: количество, дата и порядковый номер покупки, идентичность операции покупки, номинал, остаток стоимости тела, капитальные расходы, НКД при покупке (R8.25).
- **Порядковый номер покупки** (`sequence`) — номер операции покупки в ledger: задается явным параметром и проверяется (R8.27).
- **FIFO** — порядок списания лотов: по дате приобретения, при равенстве — по порядковому номеру покупки (R8.26).
- **Минимальная единица валюты** — `10^(−defaultFractionDigits)` валюты (для RUB — копейка).
- **Удержание** — фактически удержанные деньги на счете `TAX_WITHHELD` (adjustable-роль, R5.2).
- **Налоговая часть** — суммы налоговых видов и налоговые параметры `WITHDRAWAL` при `taxToWithhold > 0`; валюта — RUB (R8.8, AD-15).
- **Неудержанный налог** — факт из taxation R7.4 и R7.7; сущностью ledger не является, фиксируется в application (N10, AD-16).
- В прозе v1.0.0 вид «BUY» соответствует значению enum `PURCHASE`; в v2.0.0 используется имя enum `PURCHASE`.
- `OperationRecord.sequence` (порт application, журнал) и `Lot.sequence` — разные понятия: `Lot.sequence` определяется по ledger (R8.27).

## 3. Цели, assumptions, non-goals

**Цели:** R0.1 (раздел 1) и:

- **R0.2** — финансовая семантика v1.0.0 сохраняется, кроме изменений, перечисленных в разделе 14 (п. 9): списание по лотам (R8.13, R8.26), округление частичных списаний вниз по минимальной единице валюты (R8.15, AD-31), амортизационное распределение по номиналу лотов (R8.12, AD-30), явное распределение НКД при купоне (R8.11, AD-32). Для позиции из одного лота результат совпадает с v1.0.0 с точностью до одной минимальной единицы валюты на операцию, где v1.0.0 округлял иначе (DE-P-35). `WITHDRAWAL` при `taxToWithhold = 0` идентичен v1.0.0 (R8.9).
- **R0.3** — состояние ledger самодостаточно, включая лоты и историю: восстановление и независимая перепроверка (`LedgerCommit`, `InMemoryLedgerRepository`) возможны без внешней конфигурации.
- **R0.4** — конфигурация (chart и policy) передается через конструкторы; per-call chart в сигнатурах операций не передается.
- **R0.5–R0.7** — раздел 1.

**Assumptions (предпосылки):**

- **A1** — внешних потребителей публичного API `core.ledger` нет. Подтверждено пользователем 2026-10-21 для v1.0.0 и повторно подтверждено для v2.0.0 (AD-36).
- **A2** — persistence только in-memory: миграция persisted-данных не требуется; `LedgerState` не имеет внешнего сериализованного формата. Персистентный слой вне версии (AD-36).
- **A3** — JDK 25; JUnit Jupiter 5.12.2; новых production-зависимостей нет.
- **A4** — налоговые величины (ставки, YTD, `YearTax`, `AlreadyWithheld`, `TaxOnExcess`, даты `ClosingDate` и `TermEndDate`, признаки счета) вычисляются вызывающим вне подсистемы и передаются явно (taxation §1; Д6). Движок и сервисы ledger налог не вычисляют и календарных признаков не определяют.

**Границы доверия (нормативно):**

- **TR1** — аутентификации и авторизации нет (N7). Известность кода по chart не равна доверенности.
- **TR2** — первый успешный commit выбирает chart портфеля (R11.4); CAS арбитрирует конкурентных писателей, подлинность chart не гарантируется.
- **TR3** — движок валидирует форму операции (баланс, роли, scoping, adjustment-связи, форму налоговых проводок R9.9, FIFO-форму изменения лотов R7.6b), а не экономическое происхождение. Сервисы публично принимают произвольный `OperationResult`; совпадение словаря с policy гарантируется сборкой (R8.3). Restore не различает виды корректировок по знаку (AD-37).
- **TR4** — движок не выводит, какие конкретно лоты списаны и каким округлением; он проверяет форму изменения списка лотов (R7.6b), соответствие сумм лотов балансам (R7.9) и инварианты лотов (R9.7).

**Non-goals (явные отказы):**

- **N1** — без DSL, rule engine, иерархий счетов, multi-book, strategy-интерфейсов; роли движка — закрытый набор (раздел 5).
- **N2** — `Position` остается bond-моделью движка; лоты — ее часть. Quantity НЕ становится измерением ledger-счета: остается атрибутом позиции под защитой stale-snapshot (R7.6) и FIFO-формы (R7.6b).
- **N3** — смена chart в течение жизни ledger запрещена (R6.7).
- **N4** — метаданные «normal balance» не вводятся: соглашение знаков прежнее (positive = debit, negative = credit). Знаковая интерпретация обязательства (L = −баланс) задана в R9.8.
- **N5** — новые пакеты, модули и exports не вводятся; `Lot` размещается в `core.ledger`.
- **N6** — `OperationKind` и enum-диспетчеризация, включая налоговые виды, сохраняются (AD-6).
- **N7** — аутентификация и авторизация chart и операций не вводятся.
- **N8** — учет замещающих облигаций с валютой номинала, отличной от валюты расчетов, и валютный пересчет — отдельная спецификация. Налоговая часть — RUB (R8.8).
- **N9** — расчет налога и ставок, YTD, сальдирование убытков и перенос убытков (taxation R3.2, R4, R8.3 `Result`/`RealizedLoss`, R8.6) не входят в ledger; налоговые суммы передаются явно (A4).
- **N10** — «неудержанный налог» (taxation R7.4, R7.7) не является сущностью ledger и не проводится; факт фиксируется в application (AD-16).
- **N11** — ledger не знает ИИС-3, срока, лимита вычета, резидентства и не определяет досрочность закрытия (taxation R7.7); ledger получает явные суммы (R8.22, R10.7).
- **N12** — история проводок не хранит количество бумаг и номинал; `Posting` не меняется. Восстановление не сверяет количество позиции и номинал лотов с историей. Это не регрессия относительно v1.0.0: там количество позиции также не сверялось с историей (AD-34).
- **N13** — налоговая база НКД первого купона (taxation R1.5) вне ledger. Ledger уменьшает НКД лота только по явному распределению, которое передает вызывающий (R8.11).
- **N14** — налоговый счет расхода не вводится: НДФЛ физического лица не является расходом, вычитаемым из торгового дохода (taxation R7.1).

## 4. Обзор целевой архитектуры

Три слоя, как в v1.0.0, с уточнениями:

1. **Движок** (`Ledger`, `Posting`, `Account`, `LedgerState`, `Position`, `Lot`, `LedgerChart`, `AccountCode`, `PositionMeasure`): балансировка по валютам, идентичность операций, дедуп, backdating-guard, portfolio-scoping, append-only история, replay-валидация, ролевые инварианты, форма налоговых проводок, FIFO-форма лотов, инвариант доступных средств. Ноль имен счетов.
2. **Chart** (`LedgerChart`): известные коды, роли и скалярные привязки. Роль `liability` задает налоговое обязательство; привязка `deferredOffset` задает контрсчет только для проверки формы (R5.11). Заморожен в `LedgerState`.
3. **Bond-слой** (`BondAccountingPolicy` — единственный источник словаря из 11 кодов; `BondOperations` — instance-генератор проводок и лотов): единственный эмиттер кодов в postings.

**Уточнение 1.** Налоговые суммы, выбор налоговой операции (вид и сумма), распределение НКД при купоне и распределение амортизации по лотам (в пределах правил R8.12, R8.26) задает вызывающий слой (application). Ledger налог не считает (R10.7).

**Уточнение 2.** Лоты — часть `Position`, а значит и `LedgerState`; отдельного компонента состояния для лотов нет (R6.9).

Инвариант целостности: генератор и валидатор пользуются кодами одной `BondAccountingPolicy` (R8.3). Это гарантия сборки, а не движка: `Ledger.apply` публично принимает любой `OperationResult` и проверяет форму, не происхождение (TR3, TR4).

## 5. Тип `AccountCode` и роль-модель `LedgerChart`

### 5.1. `AccountCode`

```java
// core.ledger, файл AccountCode.java
public record AccountCode(String value) {
    public AccountCode {
        Objects.requireNonNull(value, "value");
        // R5.1: формат ^[A-Z][A-Z0-9_]{0,31}$ (1..32 символа, ASCII).
        // Нарушение -> IllegalArgumentException("Invalid account code: ...")
    }
    public static AccountCode of(String value) { return new AccountCode(value); }
}
```

- **R5.1** — формат кода: `^[A-Z][A-Z0-9_]{0,31}$`. Нарушение — `IllegalArgumentException` из compact-constructor.
- **R5.2** — equality/hashCode — record-семантика по `value`; natural ordering не вводится (сортировка в коллекциях chart — по `value` через comparator).
- **R5.3** — код — единственная идентичность вида счета; alias и синонимы кодов не поддерживаются.

### 5.2. Роли и скалярные привязки движка (закрытый набор)

| Роль / привязка | Смысл для движка | Стандартное значение |
|---|---|---|
| `spendable` | входит в read views денежных остатков `cashBalances()` и `availableCashBalances()` (R7.16) | `{CASH}` |
| `noNegative` | запрет отрицательного остатка счета при `!allowNegativeCash` | `{CASH}` |
| `adjustable` (ровно один код) | накопительный счет фактически удержанного налога: `taxWithheldBalances()`, `taxWithheldForOperation`, adjustments | `TAX_WITHHELD` |
| `adjustmentCounterpart` (∈ spendable) | счет-партнер transfer-пары adjustment | `CASH` |
| `securityScoped` | измерение security; валюта ≡ валюте Position; обязан иметь position binding | `{SECURITIES, ACCRUED_INTEREST}` |
| `positionBinding` (securityScoped → measure) | баланс вида обязан равняться mirror-полю Position | SECURITIES→CARRYING, ACCRUED_INTEREST→PURCHASED_ACCRUED |
| `liability` (ровно один код) | налоговое обязательство L = −знаковый баланс; учитывается в `availableCashBalances()`, налоговых лимитах (R7.17), инварианте доступных средств (R7.18), знаке L (R9.8), форме налоговых проводок (R9.9) | `TAX_LIABILITY` |
| `deferredOffset` (ровно один код) | контрсчет обязательства; без влияния на балансы и лимиты; только проверка формы налоговых проводок (R9.9) | `TAX_DEFERRED_OFFSET` |

- **R5.2a — налоговые счета (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-10, AD-24, AD-25).** `TAX_LIABILITY` получает роль `liability`. `TAX_DEFERRED_OFFSET` получает скалярную привязку `deferredOffset` без поведения баланса. Прочие пассивные счета (`EQUITY`, `COUPON_INCOME`, `COMMISSION_EXPENSE`, `REALIZED_PNL`, `AMORTIZATION_GAIN`) остаются без ролей (R5.8). Adjustable-роль остается за `TAX_WITHHELD` (фактически удержанные деньги); `TAX_CORRECTION` и `TAX_REFUND` работают только по `TAX_WITHHELD`.
- **R5.2b — обоснование привязки `deferredOffset` (AD-25).** Движок проверяет форму налоговых проводок (R9.9) по идентичности кодов. Без кода контрсчета проверка не отличала бы парную налоговую проводку от проводки с произвольным пассивным контрсчетом (например, `EQUITY` или `COUPON_INCOME`), а TR3 требует проверки формы. Поведенческая роль (`spendable`, `noNegative`, `adjustable`) для контрсчета неприменима: она исказила бы денежную семантику. Выбрана минимальная скалярная привязка, не влияющая на балансы.

```java
// core.ledger, файл PositionMeasure.java (без изменений)
public enum PositionMeasure { CARRYING, PURCHASED_ACCRUED }
// CARRYING -> Position.carryingAmount(); PURCHASED_ACCRUED -> Position.purchasedAccrued().
```

### 5.3. `LedgerChart`

```java

    public Set<AccountCode> knownCodes();
    public boolean isKnown(AccountCode code);
    public Set<AccountCode> spendableCodes();
    public boolean isSpendable(AccountCode code);
    public AccountCode adjustableCode();
    public AccountCode adjustmentCounterpartCode();
    public Set<AccountCode> noNegativeCodes();
    public boolean isNoNegative(AccountCode code);
    public Set<AccountCode> securityScopedCodes();
    public boolean isSecurityScoped(AccountCode code);
    public Map<AccountCode, PositionMeasure> positionBindings();
    public PositionMeasure positionBinding(AccountCode code); // только для securityScoped
    public AccountCode liabilityCode();                       // новое
    public AccountCode deferredOffsetCode();                  // новое
    // equals/hashCode — value-семантика по всем компонентам, включая liabilityCode и deferredOffsetCode (R5.10)
}
```

Нормативные ограничения конструктора `LedgerChart`:

**Null-дисциплина (R5.4):** любой `null`-компонент — `NullPointerException` (отдельно от `IllegalArgumentException` семантических нарушений).

**Семантические ограничения (нарушение — `IllegalArgumentException` из конструктора):**

- **R5.5** — `knownCodes` непусто; все роль-множества и коды ролей — подмножества `knownCodes` (`spendable ⊆ known`, `noNegative ⊆ known`, `securityScoped ⊆ known`, `adjustableCode ∈ known`, `adjustmentCounterpartCode ∈ known`, `dom(positionBindings) ⊆ known`, `liabilityCode ∈ known`, `deferredOffsetCode ∈ known`).
- **R5.6** — матрица совместимости ролей:
  - `adjustableCode` не пересекается ни с `spendable`, ни с `noNegative`, ни с `securityScoped`;
  - `adjustmentCounterpartCode` ∈ `spendable`, плоский (`∉ securityScoped`), отличен от `adjustableCode`;
  - `spendable` — только плоские коды (`spendable ∩ securityScoped = ∅`);
  - `noNegative ⊆ spendable`;
  - `spendable` содержит ровно один код; `noNegative` — не более одного (пустое допустимо); мощность ограничена контрактом, а не типом коллекции;
  - `securityScoped`-коды обязаны иметь привязку, плоские — не обязаны.
- **R5.7** — `positionBindings`: domain ровно `securityScopedCodes`; обе меры `PositionMeasure` используются, каждая ровно одним кодом (alias-запрет).
- **R5.8** — известные коды без ролей и привязок — пассивные плоские счета: движок не дает им поведения, только хранит балансы; security у них запрещена (scoping R7.7, R9.3). В стандартном chart к ним относятся `EQUITY`, `COUPON_INCOME`, `COMMISSION_EXPENSE`, `REALIZED_PNL`, `AMORTIZATION_GAIN`. Поддержка дополнительных известных кодов без ролей обязательна (AD-5).
- **R5.9** — `positionBinding(code)` для кода `∉ securityScoped` → `IllegalArgumentException("Account code is not security-scoped: …")` (текст — диагностика, R12.1).
- **R5.10** — `LedgerChart` неизменяем; возвращаемые коллекции неизменяемы; порядок итерации детерминирован (по `value` кода); `equals`/`hashCode` — value-семантика по всем компонентам (включая `liabilityCode` и `deferredOffsetCode`), не зависящая от порядка вставки (используется в CAS, R6.4).
- **R5.11 — скалярные привязки налогового обязательства (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-24, AD-25).** Обе привязки обязательны, ровно один код каждая:
  - **(a) `liabilityCode`:** non-null (NPE); `∈ knownCodes`; плоский (`∉ securityScoped`); `∉ spendable`, `∉ noNegative`; отличен от `adjustableCode`, `adjustmentCounterpartCode` и `deferredOffsetCode`. Нарушение — `IllegalArgumentException` (`null` — NPE).
  - **(b) `deferredOffsetCode`:** non-null (NPE); `∈ knownCodes`; плоский; `∉ spendable`, `∉ noNegative`, `∉ securityScoped`; отличен от `adjustableCode`, `adjustmentCounterpartCode` и `liabilityCode`. Нарушение — `IllegalArgumentException` (`null` — NPE).
  - Ни одна из привязок не добавляется в `spendable`, `noNegative` или `positionBindings`; обе не меняют `cashBalances()`, `taxWithheldBalances()` и условие `noNegative`.

## 6. `Account`, `LedgerState`, позиции с лотами, заморозка chart

### 6.1. `Account` (без изменений)

```java
// core.ledger, Account.java
public record Account(PortfolioId portfolio, AccountCode code,
                      Optional<SecurityId> security, Currency currency) {
    public Account {
        // non-null всех компонентов; code проходит валидацию AccountCode;
        // R6.1: pseudo-currency guard: defaultFractionDigits < 0 -> IllegalArgumentException.
        // R6.2: НЕ проверяет security-scoping — chart недоступен.
    }
}
```

- **R6.1** — идентичность счета: `(portfolio, code, security?, currency)`; record-equality по четырем компонентам; map-ключ в balances.
- **R6.2** — `Account` не знает chart. Правило присутствия security (`security.isPresent() ⇔ isSecurityScoped(code)`) проверяется только в `Ledger.apply`/`Ledger.restore` (R7.7, R9.2–R9.3) и при запросе баланса (R7.15). Создание `Account` с кодом вне known или неверным scoping само по себе ошибкой не является.

### 6.2. `LedgerState`

```java
// core.ledger, LedgerState.java: состав компонентов не меняется; меняется тип значения Position
public record LedgerState(PortfolioId portfolio, LedgerChart chart,
                          boolean allowNegativeCash,
                          Map<Account, Money> balances,
                          Map<SecurityId, Position> positions,       // Position содержит лоты (R8.16)
                          NavigableMap<LocalDate, List<Posting>> postingsByDate,
                          Set<OperationId> operationIds)
```

- **R6.3** — `chart` — обязательный компонент; `null` → `NullPointerException`. Compact-constructor делает защитные копии всех коллекций (`balances`/`positions` — unmodifiable map-копии; история — `TreeMap` с `List.copyOf`-бакетами; `operationIds` — `Set.copyOf`); null-ключи и значения → NPE. Глубокая валидация — в `Ledger.restore` (R9.x).
- **R6.4** — record-equality `LedgerState` включает `chart` и `positions` (вместе с лотами); CAS-сравнение состояний охватывает chart и лоты: два разных chart и два состояния с разными лотами не алиасятся.
- **R6.5** — самодостаточность: `Ledger.restore(state)` восстанавливает ledger вместе с его chart без внешних параметров. Смешение конфигурации сервиса с persisted-состоянием запрещено и обнаруживается (R10.4, R10.5).
- **R6.6** — пустота state: `balances`, `positions`, история и `operationIds` пусты. Позиция с `quantity = 0`, сохраненная после полного выбытия (R6.10), делает state непустым. Chart в проверку пустоты не входит.

### 6.3. Заморозка chart (без изменений)

- **R6.7** — chart фиксируется при `Ledger.open` и неизменен всю жизнь ledger: `apply` возвращает новый `Ledger` с тем же chart; смена отклоняется структурно (переходы состояния строятся только через `apply`).
- **R6.8** — identity-семантика: ledger идентифицируется `(portfolio, chart, allowNegativeCash)`; смена любого из трех = другой ledger (проверки — R10.2, R10.4, R10.5, R11.2).

### 6.4. Позиции и лоты в состоянии (новое)

- **R6.9** — `LedgerState.positions()` отображает идентичность бумаги в `Position`; `Position` содержит упорядоченный список лотов (R8.16, R8.25). Лоты — часть состояния: входят в record-equality `LedgerState`, в CAS-сравнение (`LedgerCommit`, R11.2), в `Ledger.restore` (R9.7) и в snapshot (`LedgerSnapshot`). Состав компонентов `LedgerState` не меняется; меняется тип значения `Position`.
- **R6.10** — позиция не удаляется из `positions` при полном выбытии бумаг: сохраняется `Position` с `quantity == 0` и пустым списком лотов (R8.13). Это требуется R9.2 (ужесточение, AD-14).
- **R6.11** — `Ledger.position(security)` и `Ledger.positions()` возвращают неизменяемые значения с лотами; изменение лотов возможно только через `apply`.

## 7. `Ledger`: API и семантика `apply`

### 7.1. Сигнатуры

```java
public final class Ledger {
    // R7.1: единственные фабрики; overload-ы open(portfolio) и open(portfolio, allowNegativeCash) отсутствуют (AD-2, v1.0.0).
    public static Ledger open(PortfolioId portfolio, LedgerChart chart, boolean allowNegativeCash);
    // R7.2: restore — сигнатура не меняется; chart читается из state.
    public static Ledger restore(LedgerState state);

    public LedgerChart chart();
    public Ledger apply(OperationResult result);                         // сигнатура не меняется
    public Money balance(Account account);                               // R7.15
    public Map<Account, Money> balances();
    public Map<Currency, Money> cashBalances();                          // R7.12, без изменений
    public Map<Currency, Money> availableCashBalances();                 // R7.16, новое
    public Map<Currency, Money> taxWithheldBalances();                   // R7.13, без изменений
    public Money taxWithheldForOperation(OperationId originalOperation); // R7.14
    public Optional<Position> position(SecurityId security);             // Position содержит лоты
    public Map<SecurityId, Position> positions();
    public NavigableMap<LocalDate, List<Posting>> postingsByDate();
    public Set<OperationId> operationIds();
    public LedgerState state();                                          // включает chart и лоты
}
```

- **R7.1** — `open(portfolio, chart, allowNegativeCash)`: пустые balances, positions и история; `null`-chart → NPE.
- **R7.2** — `restore(state)`: сигнатура прежняя; проверка структурной согласованности (раздел 9), включая лоты (R9.7), знаковый инвариант обязательства (R9.8) и форму налоговых проводок (R9.9).

### 7.2. `apply` — нормативная последовательность

`apply(OperationResult)` возвращает новый неизменяемый `Ledger` (`this` не мутирует) и выполняет проверки в порядке ниже; первое нарушение — исключение (типы — раздел 12).

1. **R7.3 (identity)** — `result.operation()` уже в `operationIds` → `IllegalStateException("Duplicate operation ID: …")`.
2. **R7.4 (chronology)** — `result.date()` раньше последней даты истории → `IllegalStateException("Backdated operation …")`.
3. **R7.5 (dispatch)** — диспетчеризация enum-based (N6). `kind ∈ {TAX_CORRECTION, TAX_REFUND}` → валидация adjustment (раздел 10.2). Виды `WITHDRAWAL`, `TAX_ACCRUAL`, `TAX_SETTLEMENT`, `TAX_RELEASE` проверяются шагами 10 и 12 (R7.17, R7.18); формы — шагом 7 (R8.21–R8.24).
4. **R7.6 (position snapshots)** — при наличии `positionBefore`/`positionAfter`: обе принадлежат портфелю ledger; `before.id() == after.id()`; хранимая позиция по security равна `before` целиком, включая лоты (иначе `IllegalStateException("Stale position snapshot …")`; отсутствующая позиция трактуется как `Position.empty(before.id(), before.currency())`); валюта `before` == валюта `after`.
5. **R7.6a (PURCHASE)** — для `kind == PURCHASE`: `after.lots() == before.lots() + [лот покупки]` (новый лот — последним); `lot.purchaseOperation == result.operation()`; `lot.acquisitionDate == result.date()`; `lot.sequence == |operationIds| + 1` (R8.27). Нарушение — `IllegalStateException`.
6. **R7.6b (FIFO-форма, SALE / AMORTIZATION / COUPON)** — форма изменения списка лотов:
   - для AMORTIZATION и COUPON список лотов сохраняет порядок, идентичности (`purchaseOperation`, `acquisitionDate`, `sequence`) и количества (`quantity`) каждого лота; суммы каждого лота не возрастают (`after ≤ before`, `≥ 0`);
   - для SALE: `after` — суффикс `before`: лоты, полностью списанные с головы списка, отсутствуют; первый лот `after` может быть уменьшен (количество и суммы не больше исходных); остальные лоты `after` совпадают с соответствующими лотами `before` поэлементно; `Σ quantity(after) < Σ quantity(before)`.
   - Нарушение — `IllegalStateException`.
7. **R7.7 (entries, scoping, валюта, форма налоговых проводок)** — для каждого entry каждого posting: identity и date posting-а совпадают с result; `account.portfolio()` == портфель ledger; **guard известности:** `chart.isKnown(code)`, иначе `IllegalStateException("Unknown account code …")`; **scoping по chart** до любого извлечения значения из `security`: `security.isPresent() ⇔ chart.isSecurityScoped(code)` (нарушение — `IllegalStateException`); для securityScoped-кода — `security == affectedSecurity` и валюта счета == валюте позиции. Unknown-код никогда не проходит молча и не трактуется как нулевой счет. Для налоговых видов (`TAX_ACCRUAL`, `TAX_SETTLEMENT`, `TAX_RELEASE`, `TAX_REFUND`, и `WITHDRAWAL` при `taxToWithhold > 0`) валюта всех entries — RUB (R8.8); нарушение — `IllegalArgumentException`. Форма налоговых проводок — R9.9; нарушение — `IllegalStateException`.
8. **R7.8 (применение балансов)** — балансы обновляются суммированием signed amounts по каждому счету; нулевые итоговые остатки удаляются из map (правило используется restore-валидацией).
9. **R7.9 (position binding)** — `validatePositionBalances` по chart: для каждой позиции `positions[k]`: баланс счета (portfolio, код с привязкой CARRYING, security = k, валюта позиции) == `position.carryingAmount()` (= Σ `remainingCost` лотов); баланс счета с привязкой PURCHASED_ACCRUED == `position.purchasedAccrued()` (= Σ `acquiredAccruedInterest` лотов); каждый securityScoped остаток имеет позицию той же валюты. Нарушение — `IllegalStateException`.
10. **R7.17 (налоговые лимиты, IAE)** — проверки (a)–(e) раздела 7.4; выполняются до шага 11, чтобы налоговые отказы имели тип IAE.
11. **R7.10 (noNegative, per-account)** — при `!allowNegativeCash`: каждый счет по отдельности (не сумма по валюте) с `chart.isNoNegative(code)` и отрицательным итогом → `IllegalStateException("Insufficient cash in …")`. Тип отказа сохраняется как в v1.0.0.
12. **R7.18 (инвариант доступных средств, IAE)** — проверка раздела 7.4 по операциям, уменьшающим CASH; выполняется после шага 11.
13. **R7.11 (история)** — postings добавляются в bucket своей даты в порядке списка; `operationIds` пополняется; возвращается новый Ledger с тем же `(portfolio, chart, allowNegativeCash)`.

`Posting` и `Posting.Entry` не меняются: баланс по каждой валюте должен быть нулевым (`UnbalancedPostingException` — подтип `IllegalArgumentException`), валюта entry == валюта счета, `adjustsOperation` не может ссылаться на собственную операцию.

### 7.3. Read views

- **R7.12** — `cashBalances()`: агрегация по валютам всех счетов с кодом роли `spendable` (стандартный chart — только `CASH`). Счета `TAX_WITHHELD` и `TAX_LIABILITY` не входят. Без изменений относительно v1.0.0.
- **R7.13** — `taxWithheldBalances()`: агрегация по валютам счетов с кодом `chart.adjustableCode()` (стандартно — `TAX_WITHHELD`). Без изменений.
- **R7.14** — `taxWithheldForOperation(originalOperation)`: поиск исходного posting-а операции, содержащего entry по счету с кодом adjustableCode и без `adjustsOperation`; накопление = исходная сумма + все суммы posting-ов с `adjustsOperation == originalOperation` (включая `TAX_CORRECTION` и `TAX_REFUND`). Запрос adjustment-операции как исходной → `IllegalArgumentException`; отсутствие исходного withholding-posting → `IllegalArgumentException`; неизвестная операция или несколько исходных → `IllegalArgumentException`.
- **R7.15** — `balance(Account)`: портфель счета обязан совпадать с портфелем ledger (`IllegalArgumentException`); код счета обязан быть известен chart и scoping-корректен, иначе `IllegalArgumentException`. Известный и корректно скопированный счет с отсутствующим балансом возвращает `Money.zero(account.currency())`.
- **R7.16 — `availableCashBalances()` (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д4, AD-13).** Для каждой валюты `c`: `cashBalances()[c]` (ноль, если ключа нет) минус `L(c)`, где `L(c)` = −(знаковый баланс счета `liabilityCode` в валюте `c`; ноль, если счета нет). Ключи — валюты, по которым есть ненулевой остаток spendable-счета или ненулевой остаток счета `liabilityCode`; значение может быть нулевым или отрицательным; результат неизменяем. Пример (RUB): CASH = 30 000, TAX_LIABILITY = 13 000 → `availableCashBalances()[RUB] = 17 000`. View не задает лимит вывода (R7.17(a)) и не запрещает траты сам по себе (R7.18).

### 7.4. Налоговые лимиты и инвариант доступных средств

**Обозначения.** `CASH_c` — баланс счета `cash` портфеля в валюте `c` до операции; `L_c` — `L(c)` до операции; `L'_c` — после проводок операции; `R` — `amount` вывода; `T` — `taxToWithhold`; `W` — `withheldAmount`; `X` — `liabilityWriteOff`; `A` — `amount` начисления; `avail_c = CASH_c − L_c`.

**R7.17 — налоговые лимиты (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-23; тип — `IllegalArgumentException`, R12.2).**

- **(a) `WITHDRAWAL` при `T > 0`:** `0 < R ≤ CASH_b`, `0 < T ≤ R`, `T ≤ L_b`. Лимит вывода — `CASH`, а не `availableCashBalances()` (AD-13, taxation R7.3). При `T = 0` шаг (a) не применяется: поведение совпадает с v1.0.0 и ограничено шагом 11 (noNegative). Решение владельца: проверка `R ≤ CASH` при `T = 0` сохраняет поведение v1.0.0 (AD-23).
- **(b) `TAX_SETTLEMENT` (W, X):** `0 < W ≤ CASH_b`, `0 ≤ X ≤ L_b`. Проверка `W ≤ CASH_b` выполняется независимо от `allowNegativeCash`.
- **(c) `TAX_RELEASE` (X):** `0 < X ≤ L_b`.
- **(d) `TAX_ACCRUAL` (A):** `A > 0` (проверяется генератором, R8.21); дополнительного лимита по CASH нет (AD-26).
- **(e) Для любой операции:** `L'_c ≥ 0` в каждой валюте (знаковый инвариант R9.8); нарушение — `IllegalArgumentException`.

**R7.18 — инвариант доступных средств (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-26; тип — `IllegalArgumentException`).** Для операции, которая уменьшает CASH в валюте `c` (чистое изменение CASH операции `ΔCASH_c < 0`, с учетом всех ее posting-ов), после применения операции `avail_c ≥ 0`, т.е. `CASH'_c ≥ L'_c`; иначе отказ. Чистое изменение CASH учитывает комиссии и внешние налоги операции. Поведение по видам:

| Вид операции | Чистое изменение CASH | Инвариант R7.18 |
|---|---|---|
| `OPENING`, `DEPOSIT` | > 0 | не применяется |
| `WITHDRAWAL` | −R (при `T > 0` и при `T = 0`) | исключен по решению владельца; лимиты — R7.17(a) |
| `PURCHASE` | −(`cashOut` + комиссия) < 0 | **применяется**: траты не могут уводить `CASH` ниже `L` (taxation R7.2) |
| `COUPON` | gross − tax ≥ 0 | не применяется |
| `AMORTIZATION` | P − tax ≥ 0 | не применяется |
| `SALE` | grossCash − комиссия − внешний налог | **применяется только при отрицательном чистом изменении**, т.е. когда комиссия и внешний налог превышают валовую выручку; комиссия сама по себе проверку не запускает, если выручка покрывает ее |
| `TAX_CORRECTION` | −signedAdjustment | **применяется при `signedAdjustment > 0`** (увеличение удержания уменьшает CASH); при уменьшении удержания не применяется. Сценарий внешней корректировки — пункт 2 раздела 20 |
| `TAX_ACCRUAL` | 0 | не применяется: начисление не уменьшает CASH и может уменьшить `avail` (допустимо; обязательство фиксируется независимо от наличия CASH, taxation R7.1) |
| `TAX_SETTLEMENT` | −W < 0 | исключен по решению владельца; лимиты — R7.17(b). Если `X < L_b`, после операции `avail` может стать отрицательным (допустимо по AD-22, см. R8.22) |
| `TAX_RELEASE` | 0 | не применяется (уменьшает L, не CASH) |
| `TAX_REFUND` | +R | не применяется (увеличивает CASH) |

Порядок относительно noNegative: при `!allowNegativeCash` отрицательный CASH по-прежнему отвергается шагом 11 (`IllegalStateException`, как в v1.0.0); шаг 12 срабатывает для `CASH ≥ 0` с `CASH < L`. Открытый вопрос об области действия инварианта при `L = 0` и `allowNegativeCash = true` — пункт 3 раздела 20.

**Проверка сценариев (результат, без изменения требований).** Инвариант R7.18 проверен на сценариях taxation и v1.0.0:

| Сценарий | Результат проверки |
|---|---|

### 8.3. Нормативные формулы проводок

**Общие правила (R8.8).**

- **Null-дисциплина:** любой `null`-аргумент — `NullPointerException`; семантические нарушения (валюта, знаки, диапазоны) — `IllegalArgumentException`. Типы не взаимозаменяемы.
- Денежные параметры операции с позицией — в валюте позиции; cash-операции — в переданной `currency`. Нарушение — `IllegalArgumentException`.
- **Налоговая часть — RUB (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-15):** `taxToWithhold` (при `> 0`), `withheldAmount`, `liabilityWriteOff`, `refundAmount`, `amount` в `taxAccrual`, а также все entries налоговых видов и `WITHDRAWAL` при `taxToWithhold > 0` — в RUB. Нарушение — `IllegalArgumentException`. Внешние налоговые суммы v1.0.0 (`taxWithheldTotal`, `taxOnGainTotal`, `taxCorrection`) RUB-ограничением не затрагиваются (AD-15).
- Налоговые суммы передаются явно. Генератор и движок их не вычисляют (N9).
- Знаковые проверки поименно: `requirePositive` (> 0) и `requireNonNegative` (≥ 0) — по перечню каждой операции.
- **Optional-семантика внешнего налога (как v1.0.0):** в `coupon`, `amortization`, `sell` параметры `taxWithheldTotal`/`taxOnGainTotal` — `Optional<Money>`; `Optional.empty()` эквивалентно нулю (налоговая проводка не создается). Такое удержание — фактический внешний факт (R1.3b), не расчет. `CouponReceiptService.confirm` (R10.6) принимает три обязательных фактических суммы.
- **Переполнение:** `buy` вычисляет `quantity' = Math.addExact(current.quantity(), quantity)`; `Position.quantity()` тем же способом (`ArithmeticException`). Остальные денежные вычисления — через `BigDecimal`.
- **Нулевые entry опускаются** (правило `signed()`). Базовый posting операции существует всегда (может содержать ноль entry). Налоговые и комиссионные posting-и создаются только при ненулевых суммах.
- Debit = положительная сумма, Credit = отрицательная (соглашение `Posting`, R8.17).
- Вид операции (`OperationKind`, 12 значений — R8.18) и инварианты `OperationResult`, `Posting`, `Commissions` — раздел 8.4.

**OPENING / DEPOSIT / WITHDRAWAL (R8.9).**

- **OPENING, DEPOSIT:** `amount` > 0 в переданной валюте; один posting `D cash[amount] / C equity[amount]`. Счета плоские. Без position snapshots.
- **WITHDRAWAL:** параметры `amount = R` (> 0, в `currency`) и `taxToWithhold = T` (≥ 0, в `currency`). Генератор: `T ≤ R` (иначе `IllegalArgumentException`); при `T > 0` валюта — RUB (иначе `IllegalArgumentException`). Перегрузка без `taxToWithhold` эквивалентна `T = Money.zero(currency)`. Один `OperationResult` (kind `WITHDRAWAL`, без position snapshots), один CAS-коммит:
  - **P1 — выплата (базовый posting):** `D equity[R − T] / C cash[R − T]`. При `T = R` posting содержит ноль entry и существует.
  - **P2 — удержание (только при `T > 0`):** `D taxWithheld[T] / C cash[T]`. Это original withholding posting (R10.3).
  - **P3 — погашение обязательства (только при `T > 0`):** `D taxLiability[T] / C taxDeferredOffset[T]` (форма — R9.9).
  - **При `T = 0`** создается один posting `D equity[R] / C cash[R]`: структура и entries совпадают с v1.0.0 (DE-P-26).
  - Ledger-лимиты: R7.17(a) (R ≤ CASH и T ≤ L при `T > 0`; при `T = 0` — только noNegative).
  - Минимум `min(TAX_LIABILITY, R)` вычисляет вызывающий (R10.7(a)); ledger проверяет границы.
  - **Пример (RUB, taxation R7.3, `TAX_LIABILITY = 13 000`, CASH ≥ 50 000):** `R = 50 000`, `T = 13 000` → P1 `D EQUITY 37 000 / C CASH 37 000`; P2 `D TAX_WITHHELD 13 000 / C CASH 13 000`; P3 `D TAX_LIABILITY 13 000 / C TAX_DEFERRED_OFFSET 13 000`; L становится 0. `R = 30 000` (весь CASH), `T = 13 000` → `NetPayout = 17 000`. `R = 10 000`, `T = 10 000` → P1 без entry (`NetPayout = 0`), L становится 3 000.

**PURCHASE (R8.10).** Вид `PURCHASE` (в прозе v1.0.0 — «BUY»).

- Параметры: `settle` (дата расчетов), `current` (позиция; может быть `Position.empty`), `purchaseSequence` (`long` ≥ 1, R8.27), `quantity` (`long` > 0), `cleanPricePerUnit` (≥ 0), `accruedPerUnit` (≥ 0), `facePerUnit` (> 0), `commissions` (`brokerCommission`, `otherCommission` ≥ 0, одна валюта; `total()`). Все суммы — в валюте позиции.
- Расчет (точно, без округления): `cleanTotal = cleanPricePerUnit × quantity`; `accruedTotal = accruedPerUnit × quantity`; `faceTotal = facePerUnit × quantity`; `cashOut = cleanTotal + accruedTotal`; `commissionTotal = commissions.total()`.
- **Новый лот** (R8.25): `Lot(op, settle, purchaseSequence, quantity, faceTotal, cleanTotal, commissionTotal, accruedTotal)`: `remainingCost = cleanTotal`, `capitalExpenses = commissionTotal` (taxation R3.3), `acquiredAccruedInterest = accruedTotal`, `faceAmount = faceTotal`.
- Позиция после: `quantity' = Math.addExact(current.quantity(), quantity)`; список лотов = список `current` + новый лот в конце (R8.26).
- Базовый posting: `D securities[cleanTotal] / D accruedInterest[accruedTotal] / C cash[cashOut]` (нулевые entry опущены).
- Commission-posting (только при `commissionTotal ≠ 0`): `D commissionExpense[commissionTotal] / C cash[commissionTotal]`. Та же сумма хранится в `capitalExpenses` лота как налоговый атрибут; отдельной проводки для атрибута нет (Д3).
- Tax-posting не создается.

**COUPON (R8.11).** `payDate`; параметры `grossCouponTotal = G`, `taxWithheldTotal` (`Optional`), `accruedAppliedByLot` — карта «идентичность лота (`purchaseOperation`) → применённая сумма НКД» (РЕШЕНИЕ ВЛАДЕЛЬЦА). Перегрузка без карты эквивалентна пустой карте.

- Валидации: позиция открыта (`quantity > 0`); `G ≥ 0`; `tax ≥ 0`; `tax ≤ G`; каждый ключ карты совпадает с `purchaseOperation` лота позиции (иначе `IllegalArgumentException`: лот не существует); каждое значение `> 0` и `≤ acquiredAccruedInterest` этого лота (иначе `IllegalArgumentException`); `Σ значений ≤ G`; все суммы — в валюте позиции.
- Итоги: `release = Σ значений` (пусто → 0); `income = G − release` (≥ 0).
- Лоты после: для каждого лота из карты `acquiredAccruedInterest' = acquiredAccruedInterest − значение`; остальные лоты и их поля не меняются. Количество, `faceAmount`, `remainingCost` и идентичность лотов не меняются.
- Позиция после: `purchasedAccrued' = purchasedAccrued − release` (следствие распределения и R7.9).
- Базовый posting: `D cash[G] / C accruedInterest[release] / C couponIncome[income]` (нулевые entry опущены).
- Tax-posting (внешнее удержание; отдельный, если `tax ≠ 0`): `D taxWithheld[tax] / C cash[tax]`.
- **Согласование налогового атрибута лота и бухгалтерского НКД (AD-32).** Атрибут `acquiredAccruedInterest` лота — налоговый атрибут, но баланс `ACCRUED_INTEREST` связан с ним инвариантом R7.9 (баланс = Σ атрибутов лотов). Поэтому снятие атрибута лота на сумму `s` проводится как `C ACCRUED_INTEREST[s]` с тем же `s` в составе `release`; структура проводок (счета, знаки) сохраняется, сумма `release` задается явным распределением. Налоговое правило R1.5 («только первый купон») ledger не вычисляет (N13).
- **Пример (RUB):** `G = 50`; лот A — `acquiredAccruedInterest 20`, лот B — `10`; карта `{A: 8}`. Итоги: `release = 8`, `income = 42`. Проводки: `D CASH 50 / C ACCRUED_INTEREST 8 / C COUPON_INCOME 42`. Лот A — `acquiredAccruedInterest 12`, лот B — `10`; баланс ACCRUED: 30 → 22 = 12 + 10 (R7.9).
- **Поведение по умолчанию (следствие AD-32):** пустая карта дает `release = 0`: НКД не снимается, `COUPON_INCOME = G`. Это отличие от автоматического снятия v1.0.0 (`release = min(purchasedAccrued, G)`); см. пункт 4 раздела 20.

**AMORTIZATION (R8.12).** `payDate`; параметры `faceReductionTotal = F`, `paymentTotal = P`, `taxWithheldTotal`.

- Валидации (как v1.0.0): позиция открыта; `F > 0`; `P ≥ 0`; `tax ≥ 0`; `tax ≤ P`; `F ≤ faceAmount()`; полное погашение (`F == faceAmount()`) требует `purchasedAccrued() == 0`.
- **Распределение F по лотам (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-30).** Пусть `S = Σ faceAmount_i` по лотам с `faceAmount_i > 0`, и `λ` — последний по порядку FIFO лот с `faceAmount_λ > 0`. Для каждого лота `i ≠ λ` с `faceAmount_i > 0`: `F_i = proportional(F, faceAmount_i, S)` (R8.15, округление вниз). Для `λ`: `F_λ = F − Σ_{i≠λ} F_i`. Лоты с `faceAmount_i = 0` получают `F_i = 0`. Инварианты: `Σ F_i = F` (точно); `0 ≤ F_i ≤ faceAmount_i`. Нарушение `F_λ ≤ faceAmount_λ` отклоняет операцию (`IllegalArgumentException`); возможный иной способ обработки — пункт 5 раздела 20.
- **Списание стоимости по лоту:** если `F_i = faceAmount_i`, то `rcR_i = remainingCost_i`; если `faceAmount_i = 0`, то `rcR_i = 0`; иначе `rcR_i = proportional(remainingCost_i, F_i, faceAmount_i)`.
- `carryingRemoved = Σ rcR_i`; `gain = P − carryingRemoved` (signed).
- **Лоты после:** `faceAmount_i' = faceAmount_i − F_i`; `remainingCost_i' = remainingCost_i − rcR_i`; количество, `capitalExpenses`, `acquiredAccruedInterest` и идентичность лота не меняются (taxation R3.3: CE и НКД не входят в `AllocatedCost`, уменьшают базу при погашении или продаже).
- **Позиция после:** `quantity` не меняется, в том числе при полном погашении номинала (R8.16); `Position.empty` не подставляется.
- Базовый posting: `D cash[P] / C securities[carryingRemoved] / C amortizationGain[gain]`.
- Tax-posting (внешнее удержание; при `tax ≠ 0`): `D taxWithheld[tax] / C cash[tax]`.
- **Пример (RUB, лоты одинакового количества):** лот A — `faceAmount 5 000`, `remainingCost 4 500`; лот B — `faceAmount 5 000`, `remainingCost 4 750`; `F = 1 000`, `P = 1 000`. `S = 10 000`; `F_A = 500`; `F_B = 500` (λ). `rcR_A = 450`, `rcR_B = 475`; `carryingRemoved = 925`; `gain = 75`. Проводки: `D CASH 1 000 / C SECURITIES 925 / C AMORTIZATION_GAIN 75`. Лоты после: A — `faceAmount 4 500`, `remainingCost 4 050`; B — `faceAmount 4 500`, `remainingCost 4 275`.
- **Пример остатка округления (RUB):** три лота, `faceAmount 3 000` и `remainingCost 3 000` каждый; `F = 1 000`, `S = 9 000`. `F_1 = proportional(1 000, 3 000, 9 000) = 333,33`; `F_2 = 333,33`; `F_3 = 1 000 − 666,66 = 333,34` (λ). `rcR_i` равны `F_i`. Σ `F_i = 1 000,00` точно.

**SALE (R8.13).** `settle`; `quantity = q`; `salePricePerUnit` (SalePrice, taxation R8.2); `accruedInterestReceived` — НКД, полученный при продаже, общей суммой за сделку (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-21); `commissions` (SaleExpenses = `commissions.total()`, taxation R8.5); `taxOnGainTotal` (`Optional`: фактически удержанный внешним агентом налог; не расчет, N9).

- Валидации: позиция открыта; `q ≥ 1` (иначе `IllegalArgumentException`); `q ≤ quantity()` (нехватка бумаг — `IllegalArgumentException`, taxation R8.2); `salePricePerUnit ≥ 0`; `accruedInterestReceived ≥ 0`; компоненты `commissions` ≥ 0 (R8.19); `tax ≥ 0`; все суммы — в валюте позиции.
- **Списание по лотам (FIFO, R8.26).** Лоты обходятся от первого. `c_i` — количество, списанное из лота `i`, `Q_i` — его количество. Для каждого затронутого лота: `removed_X_i = proportional(X_i, c_i, Q_i)` (R8.15, округление вниз) для `X ∈ {remainingCost, acquiredAccruedInterest, faceAmount, capitalExpenses}`. Если `c_i = Q_i`, лот полностью выбывает: `removed_X_i = X_i` (точный остаток, R8.15). Иначе (только последний затронутый лот) лот остается с количеством `Q_i − c_i` и суммами `X_i − removed_X_i`.
- Итоги: `carryingRemoved = Σ removed_remainingCost_i`; `accruedRelease = Σ removed_acquiredAccruedInterest_i`; `faceRemoved = Σ removed_faceAmount_i`.
- `cleanValue = salePricePerUnit × q` (точно); `grossCash = cleanValue + accruedInterestReceived`; `accruedIncome = accruedInterestReceived − accruedRelease` (signed); `realizedPnL = cleanValue − carryingRemoved` (signed).
- **Базовый posting:** `D cash[grossCash] / C securities[carryingRemoved] / C accruedInterest[accruedRelease] / C couponIncome[accruedIncome] / C realizedPnl[realizedPnL]` (signed; нулевые entry опущены). Баланс: `grossCash = carryingRemoved + accruedRelease + accruedIncome + realizedPnL`.
- **Commission-posting** (если `commissions.total() ≠ 0`): `D commissionExpense[total] / C cash[total]`.
- **Tax-posting** (если `taxOnGainTotal ≠ 0`): `D taxWithheld[tax] / C cash[tax]` (внешнее удержание, R1.3b).
- **Позиция после:** лоты — остаток по R8.26; при отсутствии лотов — `Position.empty(id, currency)` (позиция остается в `positions`, R6.10).
- **Значения проводок (AD-21):** `carrying` = `carryingRemoved` — списанная по FIFO часть `remainingCost` (для полностью списанного лота — его `remainingCost` целиком, для частично списанного — `removed_remainingCost`); `accrued` = `accruedRelease` (НКД, снятый с лотов); `couponIncome` = `accruedInterestReceived − accruedRelease`; `realizedPnl` = `cleanValue − carryingRemoved`. Капитальные расходы лотов (`capitalExpenses`) в проводках не участвуют: комиссии покупки уже проведены как `COMMISSION_EXPENSE`; `SaleExpenses` проводится своей комиссионной проводкой. Налоговый `Result` (taxation R8.3) не проводится.
- **Пример (RUB, два лота, частичная продажа, как taxation §9.3):** лот A (порядок 3) — `quantity 100`, `remainingCost 9 000`, `capitalExpenses 10`, `acquiredAccruedInterest 100`, `faceAmount 10 000`; лот B (порядок 5) — `quantity 100`, `remainingCost 9 500`, `capitalExpenses 0`, `acquiredAccruedInterest 0`, `faceAmount 10 000`. Продажа `q = 150`, `salePricePerUnit = 98`, `accruedInterestReceived = 300`, комиссия `15`. Лот A списан полностью; лот B — `c = 50`, `Q = 100`: `removed_remainingCost = 4 750`, `removed_acquiredAccruedInterest = 0`, `removed_faceAmount = 5 000` (все деления в примере точные). Итоги: `cleanValue = 14 700`; `grossCash = 15 000`; `carryingRemoved = 13 750`; `accruedRelease = 100`; `accruedIncome = 200`; `realizedPnL = 950`. Проводки: `D CASH 15 000 / C SECURITIES 13 750 / C ACCRUED_INTEREST 100 / C COUPON_INCOME 200 / C REALIZED_PNL 950`; комиссия `D COMMISSION_EXPENSE 15 / C CASH 15`. Лот B после: `quantity 50`, `remainingCost 4 750`, `faceAmount 5 000`. R7.9: SECURITIES 18 500 → 4 750 = Σ `remainingCost`.
- **Сверка с taxation §9.3 (информативно):** налоговый `Result` = 1 125 = `realizedPnL` (950) + `accruedIncome` (200) − Σ `capitalExpenses` списанных лотов (10) − `SaleExpenses` (15). Разница с ledger-P&L — капитальные расходы, уже проведенные комиссиями, и `SaleExpenses`; налоговый расчет вне ledger (N9). Совпадение с налоговым расчетом по DECIMAL128 (taxation R6.2) возможно только при точных делениях; при округлении вниз по лотам расхождение не превышает минимальной единицы валюты на каждое деление (AD-31).

**TAX_CORRECTION (R8.14).**

- Валидации: `op ≠ originalOperation`; `signedAdjustment ≠ 0` (иначе `IllegalArgumentException`); валюта — валюта `signedAdjustment` (RUB-ограничения нет, AD-15). Исходная операция не должна содержать записи по `liabilityCode` (AD-33; проверка при apply, R10.2).
- Ровно один posting с `adjustsOperation = Optional.of(originalOperation)` и двумя signed entry: `taxWithheld` — `signedAdjustment` (со знаком); `cash` — `signedAdjustment.negate()`.
- Примеры (RUB): увеличение удержания `+5,00` → TAX_WITHHELD **+5,00**, CASH **−5,00**; возврат `−3,00` → TAX_WITHHELD **−3,00**, CASH **+3,00**.
- Без position snapshots. Коррекция работает только по `TAX_WITHHELD` (R5.2a). Ограничение к источникам удержаний — AD-33.

**R8.15 — `proportional` (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-31).**

```
scale  = max(0, currency.defaultFractionDigits)          // минимальная единица валюты
result = floor_to_scale( amount × numerator / denominator )   // RoundingMode.DOWN
отказ (IllegalArgumentException "Invalid proportional removal") если:
  amount < 0, или denominator ≤ 0, или numerator < 0, или numerator > denominator
```

- Округление частичного списания — **вниз** до минимальной единицы валюты (HALF_UP v1.0.0 заменен). Остаток остается в лоте (`X − removed`, точная разность).
- При `numerator = denominator` результат точно равен `amount` (полное списание).
- При `0 ≤ numerator ≤ denominator` результат лежит в `[0, amount]`; дополнительного ограничения (cap) не требуется.
- Пример: лот стоимостью `100,00` продается по одной бумаге из трех: `proportional(100,00, 1, 3) = 33,33`, остаток `66,67`; следующая продажа одной из двух: `proportional(66,67, 1, 2) = 33,33` (`33,335` округляется вниз), остаток `33,34`; последняя бумага — полное списание `33,34`. Сумма списаний `33,33 + 33,33 + 33,34 = 100,00` (DE-P-37).

**R8.16 — инварианты позиции (v2.0.0, РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-12, AD-29).** `Position` — record `(PositionId id, Currency currency, List<Lot> lots)`.

- Производные аксессоры (агрегаты не хранятся как компоненты): `quantity()` = Σ `quantity` лотов (`Math.addExact`); `carryingAmount()` = Σ `remainingCost`; `faceAmount()` = Σ `faceAmount`; `purchasedAccrued()` = Σ `acquiredAccruedInterest`; `lots()` — неизменяемый список в порядке FIFO.
- Инварианты (`IllegalArgumentException`; null — `NullPointerException`): `currency` и `lots` non-null; `lots` защитно копируется (`List.copyOf`); все суммы каждого лота — в `currency`; лоты строго возрастают по `(acquisitionDate, sequence)`; `purchaseOperation` лотов попарно различны; `quantity() == 0` тогда и только тогда, когда `lots` пуст (следствие R8.25).
- `Position.empty(id, currency)` = `(id, currency, [])`.
- Quantity не является измерением счета (N2).

**TAX_ACCRUAL (R8.21).** Фиксация отложенного налога (taxation R7.1).

- Сигнатура: `taxAccrual(op, date, portfolio, amount)`. Валидации: `amount > 0`; RUB (иначе `IllegalArgumentException`).
- Проводка (один posting, без CASH и без позиции): `D taxDeferredOffset[A] / C taxLiability[A]`.
- Эффект: `L' = L + A`; инвариант R9.8 выполняется. Ограничений по CASH нет (R7.18: вид не уменьшает CASH).
- Источник `A` — налог события по R4, вычисленный вызывающим (N9). Пример: `A = 4 000` при `L = 0` → `L = 4 000`; CASH не меняется.

**TAX_SETTLEMENT (R8.22).** Удержание из CASH без вывода и списание обязательства (taxation R7.4, R7.7).

- Сигнатура: `taxSettlement(op, date, portfolio, withheldAmount W, liabilityWriteOff X)`. Валидации: `W > 0`; `X ≥ 0`; RUB (иначе `IllegalArgumentException`).
- Проводки (один OperationResult, kind `TAX_SETTLEMENT`, без позиции):
  - **P1 (всегда):** `D taxWithheld[W] / C cash[W]` — удержание; это original withholding posting (R10.3).
  - **P2 (только при `X > 0`):** `D taxLiability[X] / C taxDeferredOffset[X]` — списание обязательства (форма — R9.9).
- Ledger-лимиты: R7.17(b) (`W ≤ CASH_b`, `X ≤ L_b`), тип `IllegalArgumentException`.
- **`W` и `X` независимы (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-22):** допустимы `W > X` (удержание сверх списываемого обязательства, например при `Due > L`) и `X > W` (закрытие остатка без удержания в той же операции). Заполнение `W` и `X` принадлежит вызывающему (R10.7(c), (d)):
  - годовой расчет при `Due > 0`: `W = min(Due, CASH)`, `X = L` (закрытие остатка, taxation R7.4); при `W = 0` вместо этого вида — TAX_RELEASE (R8.23);
  - досрочное закрытие ИИС-3 (`EarlyClosure = true`): `W = min(L, CASH)`, `X = L` (taxation R7.7);
  - закрытие в срок и после (`EarlyClosure = false`) с `TaxOnExcess > 0`: `W = min(TaxOnExcess, CASH)`, `X = L` (taxation R7.7).
- Пример (RUB): `L = 3 000`, `Due = 2 000`, `CASH = 50 000` → `W = 2 000`, `X = 3 000`: P1 `D TAX_WITHHELD 2 000 / C CASH 2 000`; P2 `D TAX_LIABILITY 3 000 / C TAX_DEFERRED_OFFSET 3 000`; `L` становится 0.

**TAX_RELEASE (R8.23).** Закрытие обязательства без движения CASH.

- Сигнатура: `taxRelease(op, date, portfolio, liabilityWriteOff X)`. Валидации: `X > 0`; RUB.
- Проводка (один posting, без CASH): `D taxLiability[X] / C taxDeferredOffset[X]`.
- Ledger-лимит: R7.17(c) (`X ≤ L_b`).
- Применение: закрытие остатка обязательства без удержания — при `W = 0` в годовом расчете (taxation R7.4), при `TaxOnExcess = 0` (taxation R7.7).

**TAX_REFUND (R8.24; РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-17).** Возврат переплаты удержания на CASH (taxation R7.4, `Due < 0`).

- Сигнатура: `taxRefund(op, date, portfolio, originalOperation, refundAmount R)`. Валидации генератора: `op ≠ originalOperation`; `R > 0`; RUB; `originalOperation` non-null.
- **Одна операция — одно исходное удержание (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Возврат по нескольким удержаниям выполняется несколькими операциями `TAX_REFUND`, каждая со своим CAS-коммитом.
- Проводка — один posting с `adjustsOperation = Optional.of(originalOperation)`: `D cash[R] / C taxWithheld[R]` (entry CASH `+R`, entry TAX_WITHHELD `−R`).
- Эффект: CASH растет на `R`; общий TAX_WITHHELD уменьшается на `R`; накопленное удержание исходной операции (`taxWithheldForOperation`) уменьшается на `R`; `L` не меняется.
- Обоснование привязки: taxation R7.4 требует отдельный вид, не TAX_CORRECTION по TAX_WITHHELD; привязка к исходной операции нужна, чтобы накопленное удержание по каждой операции оставалось неотрицательным (R10.2, п. 6) и чтобы TAX_CORRECTION работала от актуального значения (R10.4).
- Ledger-проверки (apply, R10.2): исходная операция известна; дата не раньше исходной; форма transfer-пары; TAX_WITHHELD-entry `< 0`; валюта равна RUB и совпадает с валютой исходного удержания; `current − R ≥ 0`, `current = taxWithheldForOperation(originalOperation)`.
- Пример (RUB): исходная операция с удержанием 13 000; `R = 2 000` → проводка `D CASH 2 000 / C TAX_WITHHELD 2 000` с `adjustsOperation = O`; `taxWithheldForOperation(O) = 11 000`; последующая TAX_CORRECTION по `O` проверяет `11 000 + adjustment ≥ 0`.

### 8.4. Полные контракты неизменяемых типов (нормативно)

Типы исключений нормативны; тексты сообщений — диагностика, не контракт (R12.1). Null-дисциплина: `null`-компоненты → `NullPointerException`, всюду отдельно от `IllegalArgumentException`.

**R8.17 — `Posting`** (record `(OperationId operation, LocalDate date, List<Entry> entries, Optional<OperationId> adjustsOperation)`; convenience-конструктор без `adjustsOperation` приравнивает его к `Optional.empty()`; без изменений относительно v1.0.0):

- `entries` защитно копируются (`List.copyOf`); null-элементы → NPE. Пустой список entries допустим (базовый posting при нулевой сумме).
- `adjustsOperation` обязан быть non-null Optional; posting не может корректировать собственную операцию (`operation.equals(adjustsOperation)` → `IllegalArgumentException`).
- Баланс: сумма entry-amounts по каждой валюте обязана быть нулевой; ненулевой итог → `UnbalancedPostingException` (подтип `IllegalArgumentException`).
- `Entry` (record `(Account account, Money amount)`): валюта amount обязана равняться валюте account → иначе `IllegalArgumentException`.
- Положительная сумма = debit, отрицательная = credit.

**R8.18 — `OperationResult`** (final class; package-private конструктор, связанный с `BondOperations`, сохраняется; enum `OperationKind` содержит 12 значений: `OPENING`, `DEPOSIT`, `WITHDRAWAL`, `PURCHASE`, `COUPON`, `AMORTIZATION`, `SALE`, `TAX_CORRECTION`, `TAX_ACCRUAL`, `TAX_SETTLEMENT`, `TAX_RELEASE`, `TAX_REFUND`). Конструктор валидирует (всё — `IllegalArgumentException`, кроме NPE):

- `postings` — непустая защитная копия;
- каждый posting: `operation` и `date` совпадают с result;
- **связь с исходной операцией:** `kind ∈ {TAX_CORRECTION, TAX_REFUND}` ⇔ каждый posting содержит `adjustsOperation`; для прочих видов ни один posting не содержит `adjustsOperation` (заменяет v1.0.0-проверку `(kind == TAX_CORRECTION) == …`);
- `kind ∈ {TAX_CORRECTION, TAX_REFUND}` ⇒ ровно один posting;
- security-операции := `PURCHASE`, `COUPON`, `AMORTIZATION`, `SALE`: присутствуют обе позиции `positionBefore`/`positionAfter`; для прочих видов (`OPENING`, `DEPOSIT`, `WITHDRAWAL`, `TAX_*`) обе отсутствуют;
- security-операции: `before.id() == after.id()` и одинаковая валюта (`currency()`);
- `WITHDRAWAL` может содержать несколько posting-ов (R8.9), не имеющих связи с исходной операцией.

**R8.19 — `Commissions`** (record `(Money brokerCommission, Money otherCommission)`; без изменений относительно v1.0.0): одна валюта компонентов; оба компонента неотрицательны; `total() = brokerCommission.add(otherCommission)`.

**R8.20 — `CouponReceipt`** (application-слой; без изменений относительно v1.0.0): record `(InvestmentAccount account, PositionId position, OperationId operation, LocalDate actualDate, Money grossTotal, Money taxWithheldTotal, Money netReceivedTotal, LedgerSnapshot ledgerSnapshot)`: портфели account/position/ledgerSnapshot совпадают; три суммы неотрицательны, в одной валюте, `gross == tax + net`; `actualDate` не ранее `openingDate` ИИС-3 (при наличии); операция присутствует в `ledgerSnapshot.state().operationIds()`. Все нарушения — `IllegalArgumentException` (NPE для null).

### 8.5. Лоты: состав, порядок и списание (новое)

**R8.25 — `Lot`** (record, `core.ledger`, новый файл `Lot.java`):

```java
public record Lot(OperationId purchaseOperation, LocalDate acquisitionDate, long sequence,
                  long quantity, Money faceAmount, Money remainingCost,
                  Money capitalExpenses, Money acquiredAccruedInterest) { ... }
```

- `purchaseOperation` — идентичность операции покупки, создавшей лот (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-18);
- `acquisitionDate` — дата расчетов покупки (`settle`, taxation R8.1);
- `sequence` — порядковый номер покупки (R8.27);
- `quantity` — количество бумаг лота;
- `faceAmount` — номинал лота (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-28): нужен для распределения амортизации (taxation R8.4);
- `remainingCost` — остаток стоимости тела (`RemainingCost`, taxation R8.1, R6.1);
- `capitalExpenses` — капитальные расходы: комиссии покупки (taxation R3.3);
- `acquiredAccruedInterest` — НКД, уплаченный при покупке (taxation R3.3); налоговый атрибут, уменьшаемый при COUPON (R8.11).

Инварианты: все компоненты non-null (NPE); `quantity ≥ 1` (лот с нулевым количеством не существует: он удаляется при полном выбытии); `sequence ≥ 1`; `faceAmount`, `remainingCost`, `capitalExpenses`, `acquiredAccruedInterest` ≥ 0 и в одной валюте (`IllegalArgumentException`). Равенство валют лота и позиции проверяет `Position` (R8.16).

**R8.26 — порядок FIFO и правила изменения лотов.**

- **Порядок.** Лоты позиции упорядочены по `(acquisitionDate ASC, sequence ASC)`; этот порядок — FIFO (taxation R8.1, R8.2). Новый лот покупки добавляется в конец списка (дата покупки не раньше дат существующих лотов, R7.4).
- **Продажа (SALE).** Списание от первого лота; затронут не более чем один лот, у которого остается ненулевой остаток. Для затронутого лота `removed_X = proportional(X, c, Q)` (R8.15, округление вниз); остаток — `X − removed_X`; полностью списанный лот удаляется. Проводки — R8.13.
- **Амортизация (AMORTIZATION).** Распределение `F` по лотам — пропорционально номиналу, остаток округления — последнему лоту FIFO с ненулевым номиналом; `Σ F_i = F` точно (R8.12). Количество лотов не меняется; лоты с нулевым номиналом остаются (с `quantity ≥ 1`).
- **Купон (COUPON).** Распределение НКД — явная карта «лот → применённая сумма» (R8.11); количество и идентичности лотов не меняются, `acquiredAccruedInterest` уменьшается на переданную сумму.
- **Форма изменения списка лотов (R7.6b)** проверяется движком. Конкретный набор списанных лотов движок не выводит (TR4).
- **Налоговые атрибуты.** `capitalExpenses` и `acquiredAccruedInterest` лотов используются налоговым расчетом (taxation R3.3, R8.3); при амортизации не меняются; при продаже частично списанного лота их часть выбывает пропорционально (R8.13).

**R8.27 — порядковый номер покупки (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-18).**

- `sequence` лота задается явным параметром `purchaseSequence` операции покупки (taxation R8.1: «задается явно»). В момент применения `purchaseSequence` ДОЛЖЕН равняться `|operationIds| + 1`; иное значение — `IllegalStateException` (R7.6a). Номер совпадает с порядковым номером операции в ledger.
- Вызывающий берет `|operationIds|` из снапшота, с которым строит операцию. Номер ledger и `OperationRecord.sequence` (порт application) — разные понятия (раздел 2).
- Порядковый номер операции для восстановления (R9.7) — порядковый номер ее первого появления при реплее истории (даты по возрастанию, внутри даты — порядок списка posting-ов). `apply` дописывает postings операции в конец бакета, поэтому порядок первого появления совпадает с порядком применения.

## 9. `restore` — структурная валидация (не достижимость)

- **R9.1** — `Ledger.restore(state)` валидирует и восстанавливает состояние; сигнатура не меняется; chart берется из state (R6.5).
- **R9.2** — restore проверяет структурную согласованность (параметризованный chart):
  - балансы: portfolio-скопинг; валюта баланса == валюте счета; нулевые остатки отсутствуют; noNegative при строгой политике (`!allowNegativeCash`);
  - позиции: ключ == identity (`position.id().security()`), portfolio-скопинг;
  - **ужесточение (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-14):** каждая историческая entry по securityScoped-счету требует существующую позицию с тем же `security` и той же валютой, что у счета. Позиция учитывается независимо от сумм: нулевая позиция после полного выбытия (R6.10) удовлетворяет требованию. Прежняя формулировка v1.0.0 (ненулевые остатки, R7.9) этого не требовала; текущая реализация `Ledger.restore` проверяет именно это;
  - история: непустые date-buckets; дата posting == bucket; один operationId не встречается в нескольких датах; replay суммы == balances (zero-omission);
  - `operationIds == множество операций истории`;
  - adjustment-история (раздел 10.3), position bindings (R7.9, R9.7), знаковый инвариант обязательства (R9.8) и форма налоговых проводок (R9.9).
- **R9.3 (covering/scoping)** — каждый `Account.code` в balances и в каждом entry истории ∈ `chart.knownCodes`; известность и `security.isPresent() ⇔ chart.isSecurityScoped(code)` проверяются до любого извлечения `security`. Нарушение — `IllegalArgumentException` (сообщение — диагностика), включая scoped-код без security (не `NoSuchElementException`).
- **R9.4** — restore НЕ доказывает историческую достижимость состояния. Restore не проверяет вид операций: вид в состоянии не хранится. Знак корректировки (возврат или увеличение удержания) restore не различает (AD-37).
- **R9.5** — `LedgerSnapshot` (порт application) не меняется: его конструктор через `Ledger.restore(state)` работает по самодостаточному state.
- **R9.6** — `OperationRecord` не меняется. `OperationKind` (12 значений) и конструкторные проверки `OperationResult` — по R8.18. Диспетчеризация adjustment в `Ledger.apply` остается enum-based (R7.5, N6).
- **R9.7 — структурная согласованность лотов (новое).** Для каждого `Position` состояния:
  - (a) `position.id().portfolio()` == портфель ledger; ключ карты == security позиции (R9.2);
  - (b) порядковый номер: для каждого лота `purchaseOperation ∈ operationIds`; дата первого появления этой операции в истории == `acquisitionDate`; порядковый номер ее первого появления (R8.27) == `sequence`; иначе `IllegalArgumentException`;
  - (c) `purchaseOperation` каждого лота уникален во всем состоянии: одна покупка создает один лот в одной позиции;
  - (d) граница налогового атрибута и бухгалтерского НКД: баланс CARRYING-счета == Σ `remainingCost`, баланс PURCHASED_ACCRUED-счета == Σ `acquiredAccruedInterest` (R7.9), каждый атрибут `acquiredAccruedInterest` ≥ 0; нарушение — `IllegalArgumentException`;
  - (e) не проверяются: количество позиции (`quantity`) и номинал лотов (`faceAmount`) по истории, распределение НКД между лотами и вид операции покупки. Эти данные не хранятся в истории (N12, TR4). Это не регрессия относительно v1.0.0: там количество позиции также не сверялось с историей.
- **R9.8 — знаковый инвариант обязательства (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-19, AD-24).** Для каждой валюты знаковый баланс счета `liabilityCode` ≤ 0, т.е. `L = −баланс ≥ 0`. Нарушение — `IllegalArgumentException`. Знак следует из N4: начисление `D TAX_DEFERRED_OFFSET / C TAX_LIABILITY` делает знаковый баланс обязательства отрицательным.
- **R9.9 — форма налоговых проводок (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-25).** Для каждого posting истории и каждого posting операции в `apply`:
  - если posting содержит запись по `liabilityCode`, то он содержит ровно две записи — по `liabilityCode` и по `deferredOffsetCode` — с равными модулями сумм, противоположными знаками, в одной валюте;
  - если posting содержит запись по `deferredOffsetCode`, то он удовлетворяет тому же условию.
  Нарушение: в `apply` — `IllegalStateException`; в restore — `IllegalArgumentException`. Следствие (тест DE-P-25): баланс `deferredOffsetCode` равен минус балансу `liabilityCode` в каждой валюте.

## 10. Adjustments (налоговые корректировки), налоговые операции и CAS

### 10.1. Инварианты adjustment (R10.1)

- Append-only: корректировка — новая операция; исходная история, позиции, лоты, НКД-атрибуты, купонный доход и PnL не переписываются.
- Связь: `Posting.adjustsOperation()` → исходная операция. Adjustment на adjustment запрещен (correction-to-correction, correction-to-refund, refund-to-correction, refund-to-refund): `adjustsOperation` не может указывать на операцию, имеющую собственный link.
- Хронология: дата корректировки ≥ даты исходной операции; исходная операция уже существует в ledger.
- Валюта корректировки == валюте накопленного удержания исходной операции.
- Накопленное удержание после корректировки ≥ 0.
- `TAX_REFUND` — adjustment того же класса: уменьшает накопление исходной операции на возвращенную сумму; не меняет `TAX_LIABILITY`, позиции и лоты (AD-17).

### 10.2. Валидация в `apply` (R10.2)

При диспетчеризации `kind ∈ {TAX_CORRECTION, TAX_REFUND}` (R7.5):

1. `adjustsOperation` присутствует (гарантировано ctor `OperationResult`).
2. Исходная операция ∈ `operationIds`, иначе `IllegalStateException` («неизвестная исходная операция»).
3. Дата корректировки ≥ даты исходной (по истории), иначе `IllegalStateException`.
4. Форма transfer-пары по chart: ровно два entry; один по счету `chart.adjustableCode()` (плоский), один по счету `chart.adjustmentCounterpartCode()` (плоский); равные противоположные суммы в одной валюте; оба счета портфеля. Нарушение — `IllegalArgumentException` в `validateTaxTransferPosting`, которую `apply` оборачивает в `IllegalStateException`.
5. Ненулевая сумма (нулевая коррекция отклоняется).
6. `current = taxWithheldForOperation(original)`; валюты совпадают; `current + adjustment ≥ 0`, иначе `IllegalStateException`. Если запрос `taxWithheldForOperation` выбрасывает `IllegalArgumentException` (исходная операция — adjustment, не имеет исходного withholding-posting или неизвестна), `apply` оборачивает его в `IllegalStateException`.
7. **Знак по виду:** для `TAX_REFUND` TAX_WITHHELD-entry `< 0` (возврат уменьшает удержание); для `TAX_CORRECTION` знак любой, ненулевой. Нарушение — `IllegalStateException`.
8. **Валюта:** для `TAX_REFUND` — RUB и равна валюте исходного удержания (R8.8). Для `TAX_CORRECTION` ограничения RUB нет (AD-15).
9. **Источник удержания (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-33):** для `TAX_CORRECTION` исходная операция не содержит posting с записью по `liabilityCode` (то есть не является `WITHDRAWAL` при `T > 0` и не является `TAX_SETTLEMENT` при `X > 0`). Нарушение — `IllegalStateException`. Для таких удержаний возврат выполняется только через `TAX_REFUND`. Полное покрытие ограничения (включая `TAX_SETTLEMENT` при `X = 0`) — пункт 1 раздела 20.

### 10.3. Валидация истории в restore (R10.3)

Restore валидирует историю adjustment-ов (параметризованно по chart):

1. каждая операция, имеющая posting с `adjustsOperation`, содержит ровно один posting и не является исходной withholding-операцией;
2. каждый posting с `adjustsOperation` проходит форму transfer-пары (п. 4 R10.2) и имеет ненулевую сумму;
3. исходные withholding-posting-и (entry по коду `adjustableCode` без link): без `adjustsOperation`, форма пары, положительная сумма; не более одного исходного на операцию. Этому требованию удовлетворяют P2 `WITHDRAWAL` (R8.9), P1 `TAX_SETTLEMENT` (R8.22) и удержания v1.0.0;
4. restore обходит историю в порядке `postingsByDate`: даты по возрастанию, внутри даты — в сохраненном порядке списка posting-ов. Каждая корректировка ссылается на операцию с исходным withholding-posting, встретившимся раньше в этом порядке, и не на другую корректировку;
5. валюта корректировки == валюте исходного удержания;
6. накопленное удержание каждой исходной операции ≥ 0 после каждой корректировки в хронологии (нарушение — `IllegalArgumentException`);
7. restore не различает `TAX_CORRECTION` и `TAX_REFUND` (вид в состоянии не хранится): знак корректировки проверяется только как ненулевой; ограничение источника (R10.2, п. 9) restore не проверяет (AD-37).

### 10.4. `TaxCorrectionService` (application, без изменения сигнатуры)

```java
public TaxCorrectionService(LedgerRepository repository, BondAccountingPolicy policy)
public LedgerSnapshot correct(PortfolioId portfolio, OperationId correctionOperation,
                              LocalDate correctionDate, OperationId originalOperation,
                              Money correctedTotal, boolean allowNegativeCash)
```

- **R10.4** — сервис: `correctedTotal ≥ 0`; загрузка snapshot (отсутствие — `IllegalStateException`); **проверка chart**: `snapshot.state().chart().equals(policy.chart())`, иначе `IllegalStateException`; портфель snapshot совпадает с запрошенным (`IllegalStateException`); cash-policy; duplicate-проверка (`DuplicateOperationException`); `current = taxWithheldForOperation(original)` (включая возвраты TAX_REFUND); его `IllegalArgumentException` сервис **не оборачивает**; валюта `correctedTotal` == валюте `current` (`IllegalArgumentException`); `adjustment = correctedTotal − current`; нулевая дельта → `IllegalArgumentException`; генерация через `new BondOperations(policy).taxCorrection(...)`; `before.apply`; `repository.commit(new LedgerCommit(version, before.state(), operation, after.state()))` — без повторов конфликтов, без вычисления налога и без переписывания журнала или receipt.

### 10.5. `LedgerApplicationService` (application, без изменения сигнатуры)

```java
public LedgerApplicationService(LedgerRepository repository, BondAccountingPolicy policy)
public LedgerSnapshot apply(PortfolioId portfolio, boolean allowNegativeCash, OperationResult operation)
```

- **R10.5** — сервис: load snapshot; при загруженном snapshot — проверка портфеля (`IllegalStateException` при несовпадении), cash-policy (`allowNegativeCash == state.allowNegativeCash()`, иначе `IllegalStateException`) и **chart-консистентности** (`snapshot.state().chart().equals(policy.chart())`, иначе `IllegalStateException("Chart differs from the persisted ledger chart")`); restore; duplicate-проверка (`DuplicateOperationException`); `before.apply`; `repository.commit(new LedgerCommit(version, before.state(), operation, after.state()))` — без повторов конфликтов. При отсутствии snapshot: `Ledger.open(portfolio, policy.chart(), allowNegativeCash)`, expectedVersion = 0. Chart никогда не передается per-call — только из конструктора (R0.4). Состояния, сохраненные по схеме v1.0.0, отвергаются этой проверкой (раздел 14, S1).

### 10.6. `CouponReceiptService` (application, без изменения сигнатуры)

```java
public CouponReceiptService(InvestmentAccountRepository accounts,
                            LedgerRepository ledgers, BondAccountingPolicy policy)
public CouponReceipt confirm(InvestmentAccount account, Position position,
                             OperationId operation, LocalDate actualDate,
                             Money grossTotal, Money taxWithheldTotal,
                             Money netReceivedTotal, boolean allowNegativeCash)
```

- **R10.6** — `confirm` выполняет проверки по v1.0.0 (NPE для null; прочее — `IllegalArgumentException`, кроме отмеченного): три обязательные неотрицательные суммы одной валюты; `gross == tax + net`; портфели совпадают; `position.quantity() > 0`; метаданные счета сверяются с реестром (`IllegalStateException` — неизвестен; `IllegalArgumentException` — несовпадение); `actualDate ≥ openingDate` (при наличии); загруженный snapshot существует (`IllegalStateException`); позиция сверена с `state().positions()` (равенство включает лоты; несовпадение — `IllegalArgumentException`); операция строится `new BondOperations(policy).coupon(operation, actualDate, position, grossTotal, Optional.of(taxWithheldTotal))` (перегрузка без карты НКД: пустое распределение, AD-32) и коммитится через `LedgerApplicationService.apply(...)`; возвращается `CouponReceipt` (R8.20).

### 10.7. Ответственность application за налоговые операции (новое)

Расчет и выбор налоговых операций выполняет вызывающий слой вне ledger (taxation R7.3, R7.4, R7.7; Д6). Новых application-сервисов налоговых операций эта версия не вводит (AD-35).

- **(a) Вывод с удержанием.** Вызывающий читает `TAX_LIABILITY` из снапшота (через `policy.taxLiability()`), вычисляет `T = min(L, R)`, `NetPayout = R − T` и вызывает `BondOperations.withdrawal(…, R, T)` с последующим `LedgerApplicationService.apply`. Ограничения `R ≤ CASH` и `T ≤ L` проверяет ledger (R7.17(a)). При `T = 0` вызов эквивалентен v1.0.0.
- **(b) ИИС-3.** Операция `WITHDRAWAL` для счета ИИС-3 без закрытия счета отклоняется слоем application (`InvestmentAccount`) до ledger. Триггер годового расчета для ИИС-3 не запускает налоговое списание; `TAX_LIABILITY` продолжает копиться (taxation R7.7).
- **(c) Годовой расчет.** Вызывающий явно передает `TaxYear`, `YearTax` (с учетом сальдирования внутри года, taxation R3.2 — вне области) и `AlreadyWithheld`; вычисляет `Due = YearTax − AlreadyWithheld`. При `Due > 0`: `W = min(Due, CASH)` → TAX_SETTLEMENT (R8.22), при `W = 0` → TAX_RELEASE (R8.23); остаток обязательства закрывается до нуля (`X = L`). При `Due < 0`: переплата `−Due` возвращается **одной операцией TAX_REFUND на каждое исходное удержание** (R8.24); каждая операция — отдельный CAS-коммит. При `Due = 0` удержание не производится. Дата операции — январь года, следующего за налоговым (taxation R7.4); календарная проверка вне ledger.
- **(d) Досрочное закрытие ИИС-3.** `EarlyClosure = ClosingDate < TermEndDate` определяется вызывающим по явным датам (taxation R7.7). При досрочном закрытии: `W = min(L, CASH)`, `X = L` (TAX_SETTLEMENT). При закрытии в срок и после: `TaxOnExcess` передает вызывающий, `0 ≤ TaxOnExcess ≤ L`; `W = min(TaxOnExcess, CASH)`, `X = L`; при `TaxOnExcess = 0` — TAX_RELEASE (`X = L`). Соотношение с существующими оценками ИИС-3 application — пункт 6 раздела 20.
- **(e) Налог события.** Налог по R4 (`TAX_ACCRUAL`, R8.21) вычисляет вызывающий (taxation R4, R7.1). Ledger не знает ставок и YTD (N9).
- **(f) Распределение НКД.** Явную карту «лот → применённая сумма» (R8.11) формирует вызывающий. `CouponReceiptService` в текущей ревизии строит операцию с пустой картой (AD-32; пункт 4 раздела 20).
- **(g) Неудержанный налог.** Факт фиксируется в application (запись application-слоя), ledger его не хранит (N10, AD-16).

## 11. Порты и in-memory репозиторий

### 11.1. Неизменяемые порты

- **R11.1** — `LedgerRepository`, `LedgerJournal`, `LedgerSnapshot`, `OperationRecord`, `DuplicateOperationException`, `LedgerConcurrencyException`, `RepositoryConfig`, `LedgerRepositoryFactory.create(RepositoryConfig)` — не меняются. Сохранение `Position` с лотами (R6.9) происходит через существующие порты без изменения их сигнатур.

### 11.2. `LedgerCommit`

- Канонический конструктор: `LedgerCommit(long expectedVersion, LedgerState before, OperationResult operation, LedgerState after)`. Все объектные компоненты обязательны. `expectedVersion ≥ 0`; портфель и cash-policy before/after совпадают; при version 0 before пуст по R6.6; при version > 0 before содержит операции. Нарушения — `IllegalArgumentException`. Уже присутствующий в before operation ID отклоняется `DuplicateOperationException`. Вычисляется `Ledger.restore(before).apply(operation)`; результат обязан точно равняться after (включая лоты), иначе `IllegalArgumentException`. `portfolio()` возвращает `before.portfolio()`.
- **R11.2** — shape не меняется; ctor-валидации сохраняются, плюс явная проверка `before.chart().equals(after.chart())` — иначе `IllegalArgumentException("Commit cannot change portfolio, chart, or negative-cash policy")` (как в v1.0.0).

### 11.3. `InMemoryLedgerRepository`

- **R11.3** — без изменения кода относительно v1.0.0: `Ledger.open(commit.portfolio(), commit.before().chart(), commit.before().allowNegativeCash())` при реконструкции пустого before (версия 0). Тесты фикстур, использующие `Position` с лотами, меняются (раздел 13).
- **R11.4** — начальная запись (version 0) выбирает chart без гарантии подлинности: `LedgerCommit` требует пустой before (R6.6); репозиторий реконструирует `Ledger.open(…, before.chart(), …)` и сравнивает на точное равенство с `commit.before()`. Независимого доверенного источника chart не существует; подмена chart при первом commit не детектируется (TR2). Конкурентные первые записи с разными policy арбитрирует CAS: побеждает одна, остальные получают `LedgerConcurrencyException` (DE-N-09). Для последующих записей CAS-сравнение состояний включает chart (R6.4) и лоты (R6.9).
- **R11.5** — re-валидация `commit` (`Ledger.restore(actualBefore).apply(commit.operation())` + сравнение after) и `validateJournal` работают без изменений (самодостаточный state).
- **R11.6** — провайдер `memory`, `RepositoryConfig` без настроек, изоляция реестров, per-portfolio блокировка, полная история — без изменений.

| Chart/policy дрейф (`state.chart != policy.chart`), в т.ч. снапшот v1.0.0 (раздел 14, S1) | `IllegalStateException` | `LedgerApplicationService.apply`, `TaxCorrectionService.correct` |
| Несовпадение cash-policy | `IllegalStateException` | сервисы |
| Переполнение `long` количества (`buy`, `Position.quantity()`) | `ArithmeticException` | `BondOperations.buy` (R8.8), `Position.quantity()` |

**R12.1** — типы исключений и условия отказа нормативны; тексты сообщений — диагностика, не контракт. Реализация обязана сохранять типы и условия отказа, перечисленные здесь и в R5–R11. Тесты проверяют тип и условие отказа, но не содержимое сообщения.

**R12.2 — налоговые отказы в apply (РЕШЕНИЕ ВЛАДЕЛЬЦА, AD-23, AD-26).** Налоговые лимиты R7.17 и инвариант доступных средств R7.18 выполняются в `apply` с типом `IllegalArgumentException`, хотя общее правило `apply` для отказов состояния — `IllegalStateException`. Основание: taxation R7.3 и R7.7 («иначе IAE») и решение владельца об IAE для налоговых отказов. Тип зафиксирован тестами DE-N-20, DE-N-23, DE-N-24, DE-N-26 и DE-N-39. Отказы, которые v1.0.0 уже выражала как `IllegalStateException` (noNegative, adjustment-связи), сохраняют тип.

## 14. Совместимость и breaking-изменения (относительно v1.0.0)

Перечень относится к коду, реализующему v1.0.0 (см. индекс README). Все пункты — MAJOR; утверждаются вместе с версией.

**Ломаются (source- и binary-incompatible, если не указано иное):**

1. **`BondAccountingPolicy`** — 9 → 11 компонентов (состав record, ctor, equality); `standard()` добавляет `TAX_LIABILITY` и `TAX_DEFERRED_OFFSET`; `chart()` содержит 11 известных кодов (R8.1–R8.2).
2. **`LedgerChart`** — конструктор получает два новых параметра (`liabilityCode`, `deferredOffsetCode`) и два аксессора; equality учитывает оба кода (R5.3, R5.11). Существующие вызовы конструктора v1.0.0 не компилируются.
3. **`Position`** — shape `(id, quantity, carryingAmount, faceAmount, purchasedAccrued)` → `(id, currency, lots)`; конструктор `new Position(...)` ломается. Аксессоры `quantity()`, `carryingAmount()`, `faceAmount()`, `purchasedAccrued()` сохраняются как производные (R8.16). `Position.empty(id, currency)` сохраняется.
4. **`OperationKind`** — enum расширяется значениями `TAX_ACCRUAL`, `TAX_SETTLEMENT`, `TAX_RELEASE`, `TAX_REFUND` (всего 12). Исчерпывающие `switch` по enum ломаются.
5. **`OperationResult`** — правила конструктора: связь с исходной операцией для `TAX_REFUND`, несколько posting-ов у `WITHDRAWAL`, налоговые виды без позиций (R8.18). Валидные входы v1.0.0 остаются валидными.
6. **`BondOperations.buy(...)`** — добавлен параметр `purchaseSequence` в обоих overload-ах (R8.10, R8.27).
7. **`BondOperations.sell(...)`** — параметры переименованы и переопределены: `cleanPricePerUnit` → `salePricePerUnit`; `accruedReceivedPerUnit` → `accruedInterestReceived` (общая сумма за сделку, не за единицу; AD-21); `commission`/`Commissions` трактуются как SaleExpenses (R8.13).
8. **Финансовая семантика (MAJOR):**
   - (a) списание стоимости, НКД и номинала по лотам FIFO вместо агрегатной пропорции v1.0.0 (R8.12, R8.13, R8.26);
   - (b) частичные списания округляются вниз по минимальной единице валюты (R8.15, AD-31) вместо HALF_UP v1.0.0; результат отличается от v1.0.0 на одну минимальную единицу на операцию, где v1.0.0 округляла вверх; при полном списании лота результат точный;
   - (c) амортизация распределяется по номиналу лотов с остатком последнему лоту FIFO (R8.12, AD-30);
   - (d) **COUPON:** снятие НКД выполняется только по явной карте «лот → сумма» (R8.11, AD-32). Вызов без карты (сигнатура v1.0.0) не снимает НКД: `release = 0`, `COUPON_INCOME = G`. Автоматическое снятие v1.0.0 (`release = min(purchasedAccrued, G)`) не сохраняется; конфликт с исходными требованиями — пункт 4 раздела 20.
9. **Инвариант доступных средств (R7.18, AD-26):** операции, уменьшающие CASH, отклоняются, если после них `CASH < L`. Для портфелей без налогового обязательства при `allowNegativeCash = true` это может менять поведение v1.0.0 — пункт 3 раздела 20.
10. **Налоговые отказы в `apply` имеют тип `IllegalArgumentException`** (R7.17, R7.18, R12.2, AD-23).
11. **Ограничение источника TAX_CORRECTION (R10.2, п. 9, AD-33):** корректировка удержания, созданного `WITHDRAWAL` (T > 0) или `TAX_SETTLEMENT` (X > 0), отклоняется. Полное покрытие — пункт 1 раздела 20.
12. **`Ledger.restore`** — ужесточение R9.2 для securityScoped-истории (AD-14). Текущая реализация уже так работает; спецификация v1.0.0 этого не фиксировала. Carry-over по R9.2 закрыт этой версией.
13. **`WITHDRAWAL` при `taxToWithhold > 0`** отвергает `R > CASH` (IAE) и `T > L` (IAE). Перегрузка без налоговой части сохраняет поведение v1.0.0 (R8.9, R7.10).

**Не меняются (shape, API или поведение):** `Posting`, `Entry`, `Commissions`, `CouponReceipt`, `UnbalancedPostingException`, `LedgerSnapshot` (включая ctor-валидацию через `Ledger.restore(state)`), `OperationRecord`, `LedgerRepository`, `LedgerJournal`, `LedgerCommit` (shape; проверка R11.2 сохраняется), `RepositoryConfig`, `LedgerRepositoryFactory`, все `module-info.java`, провайдеры ServiceLoader, `Main`, `Account`, `AccountCode`, `PositionMeasure`. Сигнатуры `BondOperations.opening`, `deposit`, `taxCorrection`, `amortization`, перегрузки `withdrawal(...)` и `coupon(...)` без новых параметров не меняются (семантика `coupon` — пункт 8(d)). Сигнатуры `LedgerApplicationService`, `TaxCorrectionService`, `CouponReceiptService` (с policy) не меняются. Методы `cashBalances()`, `taxWithheldBalances()`, `taxWithheldForOperation()`, `balance()` не меняются (R7.12–R7.15).

Отсутствие deprecated-фасада сохраняется (AD-2): внешних потребителей API нет по предпосылке A1 (подтверждено для v2.0.0, AD-36).

**Исключенные требования v1.0.0 (явно; заменены указанными требованиями v2.0.0):**

- «Ровно 9 слотов» `BondAccountingPolicy` (v1.0.0 R8.1, R8.2, R8.4) — заменено 11 слотами.
- `Position` как агрегат без лотов (v1.0.0 R8.16, 5 компонентов) — заменено `Position(id, currency, lots)` и производными аксессорами (R8.16).
- Формулировка N2 v1.0.0 «атрибут `Position` под защитой stale-snapshot проверки (R7.6)» — дополнена FIFO-формой изменения лотов (R7.6b).
- Формулировка R9.2 v1.0.0 (проверка «каждый securityScoped остаток имеет позицию» только для ненулевых остатков, R7.9) — заменена ужесточением R9.2 (AD-14).
- Формулировка R0.2 v1.0.0 «финансовая семантика сохраняется бит-в-бит» — заменена R0.2 v2.0.0 с перечнем изменений (пункт 8).
- Агрегатные формулы `SALE` и `AMORTIZATION` v1.0.0 (пропорции по позиции целиком) — заменены списанием по лотам (R8.12, R8.13, R8.26).
- `accruedReceivedPerUnit` в `sell` v1.0.0 — заменено общей суммой `accruedInterestReceived` (AD-21).
- Округление HALF_UP частичного списания v1.0.0 (R8.15) — заменено округлением вниз (AD-31).
- Автоматическое снятие НКД `release = min(purchasedAccrued, G)` v1.0.0 (R8.11) — заменено явной картой (AD-32).
- R5.8 v1.0.0 (`TAX_LIABILITY` — пассивный счет без ролей) — заменено ролью `liability` (R5.2a, R5.11).
- R7.5 v1.0.0 (диспетчеризация только `TAX_CORRECTION`) — расширена на `TAX_REFUND` и налоговые виды (R7.5, R7.17, R7.18).
- Условие связи adjustment `(kind == TAX_CORRECTION) == adjustsOperation.isPresent()` (R8.18 v1.0.0) — заменено правилом для `{TAX_CORRECTION, TAX_REFUND}`.
- Требование v1.0.0 R8.9 «для WITHDRAWAL один posting; без position snapshots» — при `T > 0` заменено тремя posting-ами; при `T = 0` сохраняется (DE-P-26).

**Несовместимость со снапшотами и журналом v1.0.0.** Миграции нет (A2: in-memory; внешнего формата нет). Снапшот v1.0.0 нельзя загрузить как состояние v2.0.0:

- **S1.** `LedgerState` v1.0.0 содержит chart с 9 известными кодами и без привязок `liability`/`deferredOffset`; chart v2.0.0 содержит 11 кодов и две привязки. Сервисы отвергают снапшот (`IllegalStateException`, R10.5), `LedgerCommit` не совпадает по `before.chart()` (R11.2).
- **S2.** `Position` v1.0.0 хранит агрегаты без лотов. Лоты по агрегатам не восстанавливаются: количество и распределение стоимости по лотам в истории не хранятся (N12). `Ledger.restore` отвергает такое состояние (R9.7, `IllegalArgumentException`).
- **S3.** Equality и CAS-сравнение состояний v1.0.0 и v2.0.0 не совпадают (R6.4, R6.9).
- **S4.** Журнал операций v1.0.0 (postings) содержит виды `OPENING`, `DEPOSIT`, `WITHDRAWAL` (при `T = 0`), `PURCHASE`, `COUPON`, `AMORTIZATION`, `SALE`, `TAX_CORRECTION`; значения enum сохраняются. Балансы из журнала воспроизводятся, но лоты из журнала v1.0.0 не восстанавливаются (S2). Переход — пересоздание ledger; миграционная спецификация вне области (AD-36).
- **S5.** Новые значения `OperationKind` не встречаются в журнале v1.0.0 и не требуют его переписывания.

## 19. Решения и состояние их согласования

Статусы: **РЕШЕНИЕ ВЛАДЕЛЬЦА** — решение, внесенное по поручению владельца (задание 2026-10-22: пункты Д1–Д6 и решения по открытым вопросам). **РЕШЕНИЕ ИСПОЛНИТЕЛЯ ПО ПОРУЧЕНИЮ** — механизм или детализация, которые владелец поручил определить; их обоснование дано в тексте. Утверждение версии — отдельное действие владельца. Статус версии: DRAFT, реализация: NOT_STARTED.

- **AD-10 — структура chart (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д1).** 11 слотов `BondAccountingPolicy`; adjustable-роль — только `TAX_WITHHELD`; `TAX_LIABILITY` — роль `liability` (AD-24); `TAX_DEFERRED_OFFSET` — привязка `deferredOffset` без поведения баланса (AD-25); прочие пассивные счета — без ролей; все слоты обязательны и попарно различны; `TAX_CORRECTION` и `TAX_REFUND` работают только по `TAX_WITHHELD`.
- **AD-11 — вывод с налоговой частью и виды (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д2).** `WITHDRAWAL` с `taxToWithhold` (≥ 0; при 0 поведение идентично v1.0.0): один `OperationResult`, один CAS-коммит, проводки P1–P3 (R8.9). Минимум `min(L, R)` вычисляет application; ledger проверяет границы (R7.17(a)). Виды `TAX_ACCRUAL`, `TAX_SETTLEMENT`, `TAX_RELEASE`, `TAX_REFUND` — R8.21–R8.24.
- **AD-12 — лоты в позиции (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д3).** `Position` хранит упорядоченный список лотов; `carryingAmount` и `purchasedAccrued` — суммы по лотам; `faceAmount` и `quantity` согласованы с лотами (AD-29). Комиссия покупки остается проводкой `D COMMISSION_EXPENSE / C CASH` и хранится в лоте как налоговый атрибут без дополнительной проводки. Продажа и амортизация списывают по лотам FIFO (R8.26).
- **AD-13 — доступные средства (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д4).** Новый view `availableCashBalances()` = CASH − TAX_LIABILITY по валюте (R7.16); `cashBalances()` и `taxWithheldBalances()` не меняются; лимит вывода — CASH (R7.17(a)).
- **AD-14 — ужесточение restore (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д5).** `Ledger.restore` для securityScoped-истории требует существующую позицию той же валюты (R9.2). Ужесточение намеренное; carry-over по R9.2 из аудита v1.0.0 закрыт этой версией.
- **AD-15 — MAJOR; RUB (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д6).** Версия — MAJOR. Налоговая часть — RUB для новых налоговых видов, `WITHDRAWAL` при `T > 0` и `TAX_REFUND`; v1-пути внешнего удержания (`taxWithheldTotal`, `taxOnGainTotal`, `TAX_CORRECTION`) остаются мультивалютными; остальные операции мультивалютны (N8). Движок налог не считает (A4, N9).
- **AD-16 — неудержанный налог в application (РЕШЕНИЕ ВЛАДЕЛЬЦА, Д2).** Факт «неудержанный налог» фиксируется в application (запись application-слоя). Ledger его не хранит (N10). Носитель факта может быть изменен в будущих версиях; детали порта и записи в этой версии не проектируются.
- **AD-17 — `TAX_REFUND` с привязкой к одной исходной операции (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Возврат — отдельный вид, не `TAX_CORRECTION`; проводка `D CASH[R] / C TAX_WITHHELD[R]` с `adjustsOperation` на исходное удержание (R8.24). Одна операция — одно исходное удержание; возврат по нескольким удержаниям — несколько операций с отдельными CAS-коммитами (R10.7(c)). Непривязанный возврат не применяется: накопление по операции не должно расходиться с фактом возврата.
- **AD-18 — порядковый номер покупки и идентичность лота (РЕШЕНИЕ ВЛАДЕЛЬЦА).** `sequence` задает явный параметр `purchaseSequence`, ДОЛЖЕН равняться `|operationIds| + 1` при применении (R7.6a, R8.27). Поле `purchaseOperation` в лоте сохраняется и используется для проверки восстановления (R9.7(b)).
- **AD-19 — знак налогового обязательства (РЕШЕНИЕ ВЛАДЕЛЬЦА; производно от N4).** `L = −(знаковый баланс liability) ≥ 0`; дебетовое сальдо контрсчета `TAX_DEFERRED_OFFSET` равно `L` (taxation R7.1; R9.8).
- **AD-20 — FIFO-форма изменения лотов в apply (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Движок проверяет форму изменения списка лотов (R7.6a, R7.6b), не выводя, какие конкретные лоты списаны (TR3, TR4).
- **AD-21 — проводки продажи и сумма НКД за сделку (РЕШЕНИЕ ВЛАДЕЛЬЦА).** `carrying` — списанная часть `remainingCost` по FIFO; `accrued` — списанная часть НКД лотов; `couponIncome` = `accruedInterestReceived − accrued`; `realizedPnl` = `cleanValue − carrying`; капитальные расходы лотов в проводках не участвуют (R8.13). `accruedInterestReceived` — общая сумма за сделку; `sell` меняет семантику параметра (breaking, раздел 14).
- **AD-22 — `TAX_SETTLEMENT` (W, X) независимы (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Допустимы `W > X` и `X > W`; сценарии заполнения принадлежат вызывающему (R10.7). `TAX_RELEASE` — отдельный вид для закрытия без удержания (R8.23).
- **AD-23 — налоговые лимиты и `T = 0` (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Налоговые лимиты R7.17 — тип `IllegalArgumentException` (R12.2). Проверка `R ≤ CASH` при `T = 0` сохраняет поведение v1.0.0 (шаг 11, noNegative).
- **AD-24 — роль `liability` для `TAX_LIABILITY` (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Минимальная роль chart: ровно один плоский код; не spendable, noNegative, adjustable, counterpart и securityScoped; поведение: `availableCashBalances()` (R7.16), налоговые лимиты (R7.17), инвариант R7.18, знак L (R9.8), форма налоговых проводок (R9.9). Противоречие Д1 («без особых ролей») разрешено так: роль задает только налоговое обязательство, остальные пассивные счета ролей не получают.
- **AD-25 — привязка `deferredOffset` для `TAX_DEFERRED_OFFSET` (РЕШЕНИЕ ИСПОЛНИТЕЛЯ ПО ПОРУЧЕНИЮ).** Минимальный механизм — скалярная привязка chart без поведения баланса. Обоснование (R5.2b): проверка формы налоговых проводок требует идентичности контрсчета; без кода проверка принимала бы любой пассивный контрсчет (`EQUITY`, `COUPON_INCOME`). Поведенческая роль для контрсчета (spendable, noNegative) исказила бы денежную семантику. Альтернатива — проверка «две записи с противоположными суммами» без идентичности — отвергнута по той же причине.
- **AD-26 — инвариант доступных средств R7.18 (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Операции, уменьшающие CASH, не могут оставить `CASH < L` в своей валюте; тип — `IllegalArgumentException`. Исключены `WITHDRAWAL` и `TAX_SETTLEMENT` (собственные лимиты R7.17). Таблица поведения по видам — в R7.18 (детализация — РЕШЕНИЕ ИСПОЛНИТЕЛЯ ПО ПОРУЧЕНИЮ: сравнение по чистому изменению CASH операции, включая комиссии и внешние налоги). Открыты два конфликта — пункты 2 и 3 раздела 20.
- **AD-27 — перегрузки `withdrawal` и `coupon` (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Перегрузка без налоговой части / без карты НКД эквивалентна нулевым значениям; перегрузка с явным параметром — полная. Существующие вызовы v1.0.0 компилируются.
- **AD-28 — номинал лота (РЕШЕНИЕ ВЛАДЕЛЬЦА).** `faceAmount` хранится в каждом лоте.
- **AD-29 — агрегаты `Position` производные (РЕШЕНИЕ ВЛАДЕЛЬЦА).** `quantity`, `faceAmount`, `carryingAmount`, `purchasedAccrued` — производные от лотов; отдельных хранимых агрегатов нет (R8.16).
- **AD-30 — распределение амортизации по лотам (РЕШЕНИЕ ВЛАДЕЛЬЦА).** `F` распределяется пропорционально номиналу лота (taxation R8.4); остаток округления в минимальных единицах валюты относится к последнему лоту по порядку FIFO с ненулевым номиналом; `Σ F_i = F` точно. Детализация, принятая исполнителем по поручению: доли всех лотов, кроме последнего, округляются вниз (как в AD-31). Случай, когда остаток не помещается в номинал последнего лота, отклоняется (пункт 5 раздела 20).
- **AD-31 — округление частичного списания вниз (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Доля в минимальных единицах валюты округляется вниз, остаток остается в лоте; полное списание лота — точный остаток (R8.15). Замена HALF_UP v1.0.0: отличие на одну минимальную единицу на операцию; налоговый расчет по DECIMAL128 (taxation R6.2) расходится с ledger на минимальные единицы; это принято.
- **AD-32 — явное распределение НКД при COUPON (РЕШЕНИЕ ВЛАДЕЛЬЦА).** COUPON принимает карту «лот → применённая сумма», по умолчанию пустую. Ledger уменьшает `acquiredAccruedInterest` лота на сумму, проверяет существование лота, сумму `> 0` и `≤` значения в лоте, `Σ ≤ G`; налог ledger не считает. Согласование с R7.9: `ACCRUED_INTEREST` связан с атрибутами лотов инвариантом R7.9, поэтому снятие атрибута проводится через `C ACCRUED_INTEREST` на ту же сумму; структура проводок сохраняется. Последствие пустой карты — пункт 4 раздела 20.
- **AD-33 — источник корректировки удержания (РЕШЕНИЕ ВЛАДЕЛЬЦА).** TAX_CORRECTION разрешена только для внешних удержаний (R1.3b); для удержаний `WITHDRAWAL` (T > 0) и `TAX_SETTLEMENT` возврат — только через `TAX_REFUND`. Механизм в этой версии: отказ при apply, если исходная операция содержит запись по `liabilityCode` (R10.2, п. 9); он не покрывает `TAX_SETTLEMENT` с `X = 0`. Выбор полного механизма — пункт 1 раздела 20.
- **AD-34 — количество позиции и история (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Размер позиции определяется лотами (Σ `quantity`); `LedgerState` хранит лоты. Restore не сверяет количество и номинал лотов с историей, потому что `Posting` не хранит количество. Это не регрессия: v1.0.0 также не сверяла количество позиции с историей (N12, R9.7(e)).
- **AD-35 — application-сервисы (РЕШЕНИЕ ВЛАДЕЛЬЦА).** В этой спецификации новых application-сервисов нет; их проектирование — отдельный шаг реализации. Соотношение `EarlyClosureAssessment.additionalTax` и `TaxOnExcess` — пункт 6 раздела 20.
- **AD-36 — предпосылки и персистентность (РЕШЕНИЕ ВЛАДЕЛЬЦА).** A1 (внешних потребителей API нет) подтверждена для v2.0.0. Персистентный слой (формат, версия схемы, миграции, отказ при повреждении данных, TR2 и TR3 для персистентности) вне версии; carry-over остается в `README.md`, кроме пункта R9.2, который закрыт (AD-14).
- **AD-37 — знак корректировки в restore (РЕШЕНИЕ ВЛАДЕЛЬЦА).** Restore не различает `TAX_CORRECTION` и `TAX_REFUND` по знаку и не проверяет ограничение источника (R10.2, п. 9). Это структурное ограничение (TR3); `apply` проверяет оба правила.

Решения AD-1…AD-9 версии v1.0.0 сохраняются без изменений; их состояние — в `docs/specs/double-entry/v1.0.0.md` (неизменяемый файл). AD-2 (отсутствие deprecated-фасада) и AD-6 (enum-диспетчеризация `OperationKind`) продолжают действовать и распространяются на новые виды.

## 20. Открытые вопросы для владельца

Открытые вопросы остались только там, где правила ревизии не позволяют решить пункт исполнителю: сценарий нарушается, или решения владельца противоречат друг другу, или механизм требует изменения persisted-shape. Пункты нумеруются для ссылок из текста.

1. **Полное покрытие ограничения источника корректировки (AD-33).** Отказ по R10.2, п. 9 выявляет удержания, созданные `WITHDRAWAL` (T > 0) и `TAX_SETTLEMENT` с `X > 0`, по наличию записи по `liabilityCode` в исходной операции. Удержание `TAX_SETTLEMENT` с `X = 0` записи по обязательству не содержит и не выявляется. Варианты: (а) признак вида исходного удержания в проводке — меняет `Posting` и persisted-shape, restore и DE-тесты; (б) карта «операция → вид» в `LedgerState` — меняет `LedgerState`; (в) проверка вида исходной операции в application по журналу `OperationRecord.kind` — persisted-shape не меняет, но проверка вне движка (TR3). Выбор не сделан.

2. **Инвариант доступных средств против внешней корректировки (R7.18, TAX_CORRECTION).** Проверка сценариев показала нарушение: корректировка, которая увеличивает удержание внешнего агента (R1.3b, факт уже удержан агентом), при `avail < 0` после операции отклоняется. Отказ искажает учет зафиксированного факта. Варианты: (а) исключить корректировку внешних удержаний из R7.18 (с сохранением отказа для иных случаев); (б) оставить буквальное правило (текущий текст). Выбор не сделан.

3. **Инвариант доступных средств при `L = 0` и `allowNegativeCash = true` (R7.18).** Буквальное правило запрещает траты, уводящие CASH ниже нуля, и для портфелей без налогового обязательства, и при `allowNegativeCash = true`. Это меняет контракт v1.0.0 (DE-P-16: `allowNegativeCash = true` разрешает отрицательный остаток). Варианты: (а) применять R7.18 буквально (текущий текст); (б) применять R7.18 только при `L' > 0`, сохранив v1.0.0 для портфелей без обязательства. Выбор не сделан.

4. **Пустая карта НКД при COUPON и автоматическое снятие v1.0.0 (AD-32, R8.11).** Решение владельца «по умолчанию пустая карта» означает `release = 0`: НКД не снимается, `COUPON_INCOME = G`. Это противоречит требованию «суммарные проводки COUPON как в v1.0.0» (v1.0.0 снимала `min(purchasedAccrued, G)`) и требованию «бухгалтерский НКД в проводках не меняется»: при R7.9 баланс `ACCRUED_INTEREST` равен сумме атрибутов лотов, поэтому снятие атрибута без проводки невозможно. `CouponReceiptService` (через пустую карту) перестает снимать НКД. Варианты: (а) принять последствие как breaking-изменение (текущий текст); (б) по умолчанию снимать `min(purchasedAccrued, G)` по лотам FIFO автоматически (новое правило распределения); (в) отделить налоговый атрибут лота от бухгалтерского НКД (новое хранимое поле — меняет shape `Lot`/`Position`). Выбор не сделан.

5. **Остаток амортизационного распределения, не помещающийся в последний лот (R8.12, AD-30).** При округлении вниз долей остальных лотов остаток может превысить номинал последнего лота с ненулевым номиналом (пример: три лота номиналом `1,00` и `F = 2,99`: доли `0,99`, `0,99`, остаток `1,01 > 1,00`). Текущий текст отклоняет операцию (`IllegalArgumentException`). Варианты: (а) отклонять (текущий текст); (б) перераспределять превышение на предыдущие лоты (правило распределения не задано). Выбор не сделан.

6. **Соотношение `EarlyClosureAssessment.additionalTax` и `TaxOnExcess` (вопрос проектирования application).** В коде есть `EarlyClosureAssessment` (`returnedDeductions`, `additionalTax`, `penalties`) и `PenaltyEstimateService`. Taxation R7.7 задает `TaxOnExcess` как налог на часть результата сверх лимита вычета, но не определяет, совпадает ли `additionalTax` с ним. Вне спецификации; вопрос для проектирования application.
