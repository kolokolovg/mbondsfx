## 1. Мотивация и цель

Сегодня double-entry движок (`Ledger`, `Account`, `AccountKind`) содержит
захардкоженный план счетов bond-домена:

- `AccountKind` — закрытый enum из 9 bond-видов; `AccountKind.requiresSecurity()`
  зашивает SECURITIES/ACCRUED_INTEREST;
- `Ledger` ветвится на константы: negative-cash policy (`Ledger.apply`,
  строки 127–133 текущего кода), read views `cashBalances()`/`taxWithheldBalances()`
  (157–176), tax-correction пара TAX_WITHHELD/CASH (326–483), привязка видов к
  полям `Position` (485–510);
- `OperationResult`/`Ledger.apply` диспетчеризируют по bond-таксономии
  `OperationKind`.

Цель (R0.1): движок двойной записи не содержит **словаря счетов**; план
счетов — это данные, поставляемые composition root при открытии ledger и
замороженные в его состоянии на весь срок жизни. Bond-специфика (правила
проводок, словарь кодов) остается кодом bond-слоя (`BondOperations`,
`BondAccountingPolicy`) и невидима движку в части счетов.

**Предлагаемая граница scope (требует согласования):** таксономия операций
(`OperationKind`, включая диспетчеризацию `Ledger.apply` по
`TAX_CORRECTION`) **не** декодируется в данные и остается enum-контрактом
бонд-операций (N6); задача — dehardcode плана счетов, не таксономии
операций.

## 2. Термины

- **Движок** — универсальные части `core.ledger`: `Posting`, `Account`,
  `Ledger`, `LedgerState`, `Position`, роль-модель `LedgerChart`.
- **План счетов (chart)** — `LedgerChart`: множество известных кодов счетов и
  их роли для движка.
- **Код счета** — `AccountCode`: value-тип идентичности вида счета.
- **Bond-слой** — `BondOperations`, `BondAccountingPolicy`: эмиттеры словаря и
  правила проводок.
- **Adjustment** — append-only корректирующая операция, postings которой
  связаны с исходной операцией через `Posting.adjustsOperation()`.

## 3. Цели, assumptions, non-goals

**Цели:** R0.1 (раздел 1) плюс:

- R0.2 — вся текущая финансовая семантика (формулы проводок, округления,
  правила налоговых корректировок, CAS, append-only) сохраняется бит-в-бит;
  спецификация определяет её полностью (разделы 8–10).
- R0.3 — состояние ledger самодостаточно: восстановление и независимая
  перепроверка (`LedgerCommit`, `InMemoryLedgerRepository`) возможны без
  внешней конфигурации.
- R0.4 — отсутствие per-call протаскивания chart по сигнатурам операций;
  конфигурация — через конструкторы (constructor injection).

**Assumptions (предпосылки, не факты):**

- A1 — **предположение, требующее явного подтверждения пользователя**:
  внешних потребителей публичного API `core.ledger` нет. JPMS-инкапсуляция
  этого **не доказывает** (границы модулей ограничивают module-path
  потребителей, но не гарантируют отсутствие внешних сборок/веток/потребителей
  через root distribution). Until confirmed, breaking-изменения раздела 14
  остаются целевым предложением (AD-2).
- A2 — persistence только in-memory: миграция persisted-данных не требуется;
  `LedgerState` не имеет внешнего сериализованного формата.
- A3 — JDK 25; JUnit Jupiter 5.12.2; новых production-зависимостей нет.

**Границы доверия (нормативно):**

- TR1 — spec не вводит аутентификации/авторизации (N7). Chart «известность»
  кода ≠ доверенность: любой код, валидный по chart, принимается.
- TR2 — первый успешный commit выбирает chart портфеля (R11.4); CAS
  арбитрирует между конкурентными писателями, но **не гарантирует
  подлинность** выбранного chart.
- TR3 — движок валидирует **форму** операции (баланс, роли, scoping,
  adjustment-связи), а не её экономическое происхождение. Сервисы
  (`LedgerApplicationService.apply`) публично принимают произвольный
  `OperationResult`: совпадение словаря с policy гарантируется только
  **сборкой** (wiring: генератор и валидатор сконфигурированы одной policy,
  R8.3), а не движком. Операция с «переставленными ролями» на кодах из того
  же known-набора может пройти валидацию формы.

**Non-goals (явные отказы):**

- N1 — никаких DSL, rule engine, иерархий счетов, multi-book, strategy-
  интерфейсов; роли движка — закрытый набор (раздел 5).
- N2 — `Position` не универсализируется (остается bond-моделью в движке);
  quantity НЕ становится измерением ledger-счета — остается атрибутом
  `Position` под защитой stale-snapshot проверки (R7.6).
- N3 — смена chart в течение жизни ledger запрещена (freeze, R6.7); миграция
  chart — отдельная будущая спецификация, если потребуется.
- N4 — метаданные «normal balance»/«тип счета» для нормализации знаков НЕ
  вводятся: соглашение знаков прежнее (positive = debit, negative = credit,
  `Posting`).
- N5 — новые пакеты/модули/exports не вводятся; все новые типы — в уже
  экспортируемом `core.ledger`.
- N6 — `OperationKind` и все проверки `OperationResult` остаются как есть;
  диспетчеризация adjustment в `Ledger.apply` остается enum-based
  (`kind == TAX_CORRECTION`) — предлагаемая граница scope (раздел 1).
- N7 — аутентификация/авторизация chart и операций не вводится (границы
  доверия TR1–TR3).

## 4. Обзор целевой архитектуры

Три слоя:

1. **Движок** (`Ledger`, `Posting`, `Account`, `LedgerState`, `LedgerChart`,
   `AccountCode`, `PositionMeasure`): балансировка по валютам, идентичность
   операций, дедуп, backdating-guard, portfolio-scoping, append-only история,
   replay-валидация, ролевые инварианты. Ноль имен счетов.
2. **Chart** (`LedgerChart`): данные о том, какие коды какие роли несут;
   заморожены в `LedgerState`.
3. **Bond-слой** (`BondAccountingPolicy` — единственный источник словаря;
   `BondOperations` — instance-генератор проводок): единственный эмиттер кодов
   в postings.

Инвариант целостности: генератор и валидатор пользуются кодами одной
`BondAccountingPolicy` (R6.5, R8.3). Это **гарантия сборки (wiring)**, а не
гарантия движка: `Ledger.apply` публично принимает любой `OperationResult` и
проверяет форму, не происхождение (TR1–TR3).

## 5. Тип `AccountCode` и роль-модель `LedgerChart`

### 5.1. `AccountCode`

```java
// core.ledger, новый файл AccountCode.java
public record AccountCode(String value) {
    public AccountCode {
        Objects.requireNonNull(value, "value");
        // R5.1: формат ^[A-Z][A-Z0-9_]{0,31}$ (1..32 символа, ASCII).
        // Нарушение -> IllegalArgumentException("Invalid account code: ...")
    }
    public static AccountCode of(String value) { return new AccountCode(value); }
}
```

- R5.1 — формат кода: `^[A-Z][A-Z0-9_]{0,31}$`. Нарушение —
  `IllegalArgumentException` из compact-constructor.
- R5.2 — equality/hashCode — record-семантика по `value`; natural ordering не
  вводится (сортировка в коллекциях chart — по `value` через comparator).
- R5.3 — код — единственная идентичность вида счета; alias/синонимы кодов не
  поддерживаются.

### 5.2. Роли движка (закрытый набор)

| Роль | Смысл для движка | Стандартное значение |
|---|---|---|
| `spendable` | входит в read view «доступных» остатков (`cashBalances()`) | `{CASH}` |
| `noNegative` | запрет отрицательного остатка счета при `!allowNegativeCash` | `{CASH}` |
| `adjustable` (ровно один код) | счет накопления корректируемой величины (`taxWithheldBalances()`, `taxWithheldForOperation`) | `TAX_WITHHELD` |
| `adjustmentCounterpart` (∈ spendable) | счет-партнер transfer-пары adjustment | `CASH` |
| `securityScoped` | измерение security; валюта ≡ валюте Position; обязан иметь position binding | `{SECURITIES, ACCRUED_INTEREST}` |
| `positionBinding` (securityScoped → measure) | баланс вида обязан равняться mirror-полю `Position` | SECURITIES→CARRYING, ACCRUED_INTEREST→PURCHASED_ACCRUED |

```java
// core.ledger, новый файл PositionMeasure.java
public enum PositionMeasure { CARRYING, PURCHASED_ACCRUED }
// CARRYING -> Position.carryingAmount(); PURCHASED_ACCRUED -> Position.purchasedAccrued().
```

### 5.3. `LedgerChart`

```java
// core.ledger, новый файл LedgerChart.java
public final class LedgerChart {
    // Канонический конструктор (все коллекции копируются в сортированные
    // неизменяемые представления; итерация — в порядке value кода):
    public LedgerChart(Set<AccountCode> knownCodes,
                       Set<AccountCode> spendableCodes,
                       AccountCode adjustableCode,
                       AccountCode adjustmentCounterpartCode,
                       Set<AccountCode> noNegativeCodes,
                       Set<AccountCode> securityScopedCodes,
                       Map<AccountCode, PositionMeasure> positionBindings)

    public Set<AccountCode> knownCodes();
    public boolean isKnown(AccountCode code);
    public Set<AccountCode> spendableCodes();
    public boolean isSpendable(AccountCode code);
    public AccountCode adjustableCode();
    public AccountCode adjustmentCounterpartCode();
    public Set<AccountCode> noNegativeCodes();
    public boolean isNoNegative(AccountCode code);
    public Set<AccountCode> securityScopedCodes();
    public boolean isSecurityScoped(AccountCode code);
    public Map<AccountCode, PositionMeasure> positionBindings();
    public PositionMeasure positionBinding(AccountCode code); // только для securityScoped
    // equals/hashCode — value-семантика по всем компонентам (детерминизм — R5.10)
}
```

Нормативные ограничения конструктора `LedgerChart`:

**Null-дисциплина (R5.4):** любой `null`-компонент — `NullPointerException`
(отдельно от `IllegalArgumentException` семантических нарушений ниже).

**Семантические ограничения (нарушение — `IllegalArgumentException` из
конструктора):**

- R5.5 — `knownCodes` непусто; **все** роль-множества и отдельные коды ролей
  — подмножества `knownCodes` (`spendable ⊆ known`, `noNegative ⊆ known`,
  `securityScoped ⊆ known`, `adjustableCode ∈ known`,
  `adjustmentCounterpartCode ∈ known`, `dom(positionBindings) ⊆ known`).
- R5.6 — **матрица совместимости ролей (полная):**
  - `adjustableCode` **не пересекается** ни с `spendable`, ни с `noNegative`,
    ни с `securityScoped` (adjustable — плоский накопительный счет,
    исключенный из «доступных» остатков и из запретов отрицательности);
  - `adjustmentCounterpartCode` ∈ `spendable`, **плоский**
    (`∉ securityScoped`) и отличен от `adjustableCode`;
  - `spendable` — только **плоские** коды (`spendable ∩ securityScoped = ∅`):
    spendable-агрегация view определена по валютам, security-измерение в ней
    не участвует;
  - `noNegative ⊆ spendable`: запрет отрицательности определен только для
    доступных денежных счетов (стандартный chart: `{cash}`);
  - `securityScoped`-коды обязаны иметь привязку, плоские — не обязаны.
- R5.7 — `positionBindings`: domain **ровно** `securityScopedCodes` (каждый
  securityScoped код имеет привязку; привязка плоского кода — ошибка);
  **обе** меры `PositionMeasure` используются, каждая **ровно одним** кодом
  (alias-запрет: два кода не могут зеркалить одно поле `Position`; отсутствие
  привязки любой из мер делает R7.9 невыполнимым — отклоняется).
- R5.8 — коды без ролей (например EQUITY, COUPON_INCOME в стандартном chart)
  — **пассивные плоские** счета: движок не дает им специального поведения,
  только хранит балансы; security у пассивных кодов запрещена (scoping-правило
  R7.7/R9.2: security присутствует ⇔ код ∈ securityScoped). Поддержка
  «лишних» известных кодов — да, пассивно. `spendable` и `noNegative` могут
  быть множественными (агрегация view и per-account запрет определены для
  множеств) — целевое предложение, см. AD-4.
- R5.9 — `positionBinding(AccountCode)`: запрос для кода ∉ `securityScoped`
  → `IllegalArgumentException("Account code is not security-scoped: …")`
  (точное поведение аксессора; текст — диагностика, R12.1).
- R5.10 — `LedgerChart` неизменяем; возвращаемые коллекции неизменяемы;
  порядок итерации детерминирован (сортировка по `value` кода); `equals`/
  `hashCode` — value-семантика, не зависящая от порядка вставки (используется
  в CAS, R6.4).

## 6. `Account`, `LedgerState`, заморозка chart

### 6.1. `Account`

```java
// core.ledger, изменяется: AccountKind -> AccountCode; ctor-инвариант scoping удаляется
public record Account(PortfolioId portfolio, AccountCode code,
                      Optional<SecurityId> security, Currency currency) {
    public Account {
        // non-null всех компонентов; code проходит валидацию AccountCode;
        // R6.1: pseudo-currency guard сохраняется: defaultFractionDigits < 0
        //       -> IllegalArgumentException.
        // R6.2: НЕ проверяет security-scoping — chart недоступен.
        //       Scoping валидируется движком в apply/restore (R7.7, R9.2).
    }
}
```

- R6.1 — идентичность счета: `(portfolio, code, security?, currency)`;
  record-equality по четырем компонентам; map-ключ в balances без изменений
  семантики.
- R6.2 — `Account` не знает chart. Правило присутствия security
  (`security.isPresent() ⇔ isSecurityScoped(code)`) проверяется ТОЛЬКО в
  `Ledger.apply`/`Ledger.restore` (R7.7, R9.2) и при запросе баланса
  (R7.15). Создание `Account` с кодом вне known или неверным scoping само по
  себе ошибкой не является (value-объект); отклонение происходит при
  использовании в проводках, restore или запросе баланса.

### 6.2. `LedgerState`

```java
// core.ledger, изменяется: добавляется компонент chart (2-я позиция)
public record LedgerState(PortfolioId portfolio, LedgerChart chart,
                          boolean allowNegativeCash,
                          Map<Account, Money> balances,
                          Map<SecurityId, Position> positions,
                          NavigableMap<LocalDate, List<Posting>> postingsByDate,
                          Set<OperationId> operationIds)
```

- R6.3 — `chart` — обязательный компонент; `null` → `NullPointerException`.
  Compact-constructor: защитные копии всех коллекций (`balances`/`positions`
  — unmodifiable `LinkedHashMap`-копии; история — `TreeMap` с
  `List.copyOf`-бакетами; `operationIds` — `Set.copyOf`); null-ключи/значения
  → NPE. Глубокая валидация остается в `Ledger.restore` (R9.x) — разделение
  «state = структурная копия» vs «restore = структурная согласованность»
  сохраняется.
- R6.4 — record-equality `LedgerState` включает `chart`; CAS-сравнение
  состояний автоматически охватывает chart (два разных chart не могут
  алиаситься).
- R6.5 — самодостаточность: `Ledger.restore(state)` восстанавливает ledger
  вместе с его chart без внешних параметров. **Смешение конфигурации сервиса с
  persisted-состоянием запрещено и обнаруживается**: сервис, сконфигурированный
  policy P, обязан отвергнуть snapshot с `state.chart() != P.chart()` (R10.4,
  R10.5) — дрейф невозможен.
- R6.6 — `LedgerCommit.isEmpty`-семантика (пустой before при version 0)
  сохраняется: пустота определяется по balances/positions/postings/
  operationIds, chart в проверку пустоты не входит (пустой state несет chart).

### 6.3. Заморозка chart

- R6.7 — chart фиксируется при `Ledger.open` и неизменен всю жизнь ledger:
  `apply` возвращает новый `Ledger` с тем же chart; любые попытки смены
  отклоняются структурно (state-переходы строятся только через `apply`).
- R6.8 — identity-семантика: ledger идентифицируется `(portfolio, chart,
  allowNegativeCash)`; смена любого из трех = другой ledger (проверки
  консистентности — R10.2, R10.4, R10.5, R11.2).

## 7. `Ledger`: API и семантика apply

### 7.1. Сигнатуры

```java
public final class Ledger {
    // R7.1: единственные фабрики. Overload-ы open(portfolio) и
    // open(portfolio, allowNegativeCash) УДАЛЯЮТСЯ (AD-2).
    public static Ledger open(PortfolioId portfolio, LedgerChart chart,
                              boolean allowNegativeCash);
    // R7.2: restore — сигнатура НЕ меняется; chart читается из state.
    public static Ledger restore(LedgerState state);

    public LedgerChart chart();                       // новый accessor
    public Ledger apply(OperationResult result);      // сигнатура не меняется
    public Money balance(Account account);            // не меняется
    public Map<Account, Money> balances();            // не меняется
    public Map<Currency, Money> cashBalances();       // имя/сигнатура сохранены;
                                                      // реализация: агрегация по
                                                      // валютам счетов с ролью spendable
    public Map<Currency, Money> taxWithheldBalances();// сохранены; роль adjustable
    public Money taxWithheldForOperation(OperationId originalOperation); // сохранен
    public Optional<Position> position(SecurityId security);             // не меняется
    public Map<SecurityId, Position> positions();
    public NavigableMap<LocalDate, List<Posting>> postingsByDate();
    public Set<OperationId> operationIds();
    public LedgerState state();                       // включает chart
}
```

- R7.1 — `open(portfolio, chart, allowNegativeCash)`: пустые balances/
  positions/история; `null`-chart → NPE. Удаление старых overload-ов — часть
  breaking-решения AD-2.
- R7.2 — `restore(state)`: сигнатура прежняя; выполняет валидацию
  **структурной согласованности** (раздел 9).

### 7.2. `apply` — полная нормативная последовательность

`apply(OperationResult)` возвращает новый неизменяемый `Ledger` (текущий
`this` не мутирует) и выполняет проверки в порядке (первое нарушение —
исключение; типы — раздел 12):

1. **R7.3 (identity)** — `result.operation()` уже содержится в
   `operationIds` → `IllegalStateException("Duplicate operation ID: …")`.
2. **R7.4 (chronology)** — `result.date()` раньше последней даты истории →
   `IllegalStateException("Backdated operation …")`.
3. **R7.5 (adjustment dispatch)** — диспетчеризация остается enum-based, как
   в текущем коде: `result.kind() == OperationKind.TAX_CORRECTION` →
    валидация adjustment (раздел 10.2). Это предлагаемая граница scope
   (раздел 1, N6): dehardcode касается плана счетов, не таксономии операций;
   движок сохраняет ссылку на `OperationKind` — осознанный предел.
4. **R7.6 (position snapshots)** — при наличии `positionBefore`/`positionAfter`:
   обе принадлежат портфелю ledger; `before.id() == after.id()`; хранимая
   позиция по security равна `before` (иначе
   `IllegalStateException("Stale position snapshot …")`; отсутствующая
   позиция трактуется как `Position.empty` с валютой `before`); валюта
   `before` == валюта `after`.
5. **R7.7 (entries, включая обязательный guard неизвестных кодов)** — для
   каждого entry каждого posting: identity/date posting-а совпадают с
   result; `account.portfolio()` == портфель ledger;
   **guard известности (обязательный, явный)**: `chart.isKnown(code)` —
   код вне `knownCodes` → `IllegalStateException("Unknown account code …")`;
   **scoping по chart**: `security.isPresent() ⇔ chart.isSecurityScoped(code)`
   (нарушение любой стороны →
   `IllegalStateException("…security scoping…")`); для securityScoped:
   security == affectedSecurity (единственная затрагиваемая позиция
   операции), валюта счета == валюте позиции. Unknown-код никогда не
   проходит молча и не трактуется как нулевой счет.
6. **R7.8 (применение балансов)** — балансы обновляются суммированием signed
   amounts по каждому счету; **нулевые итоговые остатки удаляются из map**
   (правило «zero balances omitted» — сохраняется, используется restore-
   валидацией).
7. **R7.9 (position binding)** — `validatePositionBalances` по chart: для
   каждой позиции `positions[k]`: баланс счета `(portfolio, код с привязкой
   CARRYING, security=k, валюта позиции)` == `position.carryingAmount()`; код с
   привязкой PURCHASED_ACCRUED == `position.purchasedAccrued()`; каждый
   securityScoped остаток имеет соответствующую позицию той же валюты.
   Нарушение — `IllegalStateException`.
8. **R7.10 (noNegative, per-account, не агрегат)** — при
   `!allowNegativeCash`: каждый счет (по отдельности, не сумма по валюте) с
   `chart.isNoNegative(code)` и отрицательным итогом →
   `IllegalStateException("Insufficient cash in …")` (сохранение текущей
   per-account семантики; для плоских CASH-счетов эквивалентно per-currency).
9. **R7.11 (история)** — postings добавляются в bucket своей даты;
   `operationIds` пополняется; возвращается новый Ledger с тем же
   `(portfolio, chart, allowNegativeCash)`.

`Posting` и `Posting.Entry` не меняются: баланс по каждой валюте должен быть
нулевым (`UnbalancedPostingException` — подтип
`IllegalArgumentException`), валюта entry == валюта счета,
`adjustsOperation` не может ссылаться на собственную операцию.

### 7.3. Read views

- R7.12 — `cashBalances()`: агрегация по валютам всех счетов с ролью
  `spendable` (стандартный chart — только CASH; семантика «доступные для
  трат, TAX_WITHHELD не входит» сохраняется, т.к. adjustable-код не
  spendable).
- R7.13 — `taxWithheldBalances()`: агрегация по валютам всех счетов с кодом
  `chart.adjustableCode()`.
- R7.14 — `taxWithheldForOperation(originalOperation)`: поиск исходного
  posting-а операции, содержащего entry по счету с кодом adjustableCode и без
  `adjustsOperation`; накопление = исходная сумма + все суммы posting-ов с
  `adjustsOperation == originalOperation` (валидация форм — раздел 10).
  Запрос correction-операции как исходной → `IllegalArgumentException`;
  отсутствие исходной → `IllegalArgumentException`; несколько исходных →
  `IllegalArgumentException`.
- R7.15 — `balance(Account)`: портфель счета обязан совпадать с портфелем
  ledger (`IllegalArgumentException`); **код счета обязан быть
  известен chart и scoping-корректен** (`security.isPresent() ⇔
  isSecurityScoped(code)`): неизвестный код или scoping-нарушение →
  `IllegalArgumentException` — **отклонение вместо молчаливого нуля**;
  известный и корректно скопированный счет с отсутствующим балансом →
  `Money.zero(account.currency())`. **Изменение совместимости**: сегодня
  `balance()` возвращает zero для любого счета портфеля, включая
  несуществующие виды; после v1.0.0 неизвестные коды/неверный scoping
  отклоняются (см. AD-8).

## 8. Bond-слой: `BondAccountingPolicy` и instance `BondOperations`

### 8.1. `BondAccountingPolicy` — единственный источник словаря

```java
// core.ledger, новый файл BondAccountingPolicy.java
public record BondAccountingPolicy(
        AccountCode cash, AccountCode equity, AccountCode securities,
        AccountCode accruedInterest, AccountCode couponIncome,
        AccountCode amortizationGain, AccountCode realizedPnl,
        AccountCode taxWithheld, AccountCode commissionExpense) {

    public static BondAccountingPolicy standard(); // 9 кодов: "CASH","EQUITY",
        // "SECURITIES","ACCRUED_INTEREST","COUPON_INCOME","AMORTIZATION_GAIN",
        // "REALIZED_PNL","TAX_WITHHELD","COMMISSION_EXPENSE"

    // R8.1: ctor валидирует: все 9 non-null; все 9 кодов попарно различны
   //       null -> NullPointerException; повтор кода -> IllegalArgumentException.

    public LedgerChart chart();        // R8.2: чистая производная функция, детерминированная
    public BondOperations operations();// R8.3: производный configured генератор
}
```

- R8.2 — `chart()` — **чистая детерминированная производная функция** от
  9 компонентов: known = все 9; spendable = `{cash}`; noNegative = `{cash}`;
  adjustable = `taxWithheld`; counterpart = `cash`; securityScoped =
  `{securities, accruedInterest}`; bindings: `securities → CARRYING`,
  `accruedInterest → PURCHASED_ACCRUED`. Record не может иметь
  некомпонентного кеш-поля, поэтому memoизация не предписывается: свежее
  построение на каждый вызов или memo — деталь реализации, не влияющая на
  контракт; любые два вызова на равных policy дают **равный** (equal) chart.
- R8.3 — генератор проводок и валидатор получают коды из одной policy —
  согласованность словаря гарантируется **сборкой (wiring)**: composition
  root создает policy и передает её во все сервисы (R10.4–R10.6). Это
  гарантия конфигурации, **не** универсальная гарантия: `Ledger.apply`
  публично принимает любой `OperationResult`, и движок проверяет форму, а не
  происхождение (TR3); операция, сгенерированная другой policy с тем же
  known-набором, но переставленными ролями, может пройти формальную
  валидацию. Аутентификации нет (TR1).
- R8.4 — все 9 слотов обязательны (null запрещен): формулы раздела 8.3
  тотальны, опциональные слоты не вводятся.

### 8.3. Нормативные формулы проводок (полные, без «как раньше»)

Общие правила (R8.8):

- **Null-дисциплина**: любой `null`-аргумент — `NullPointerException`
  (объектные проверки `Objects.requireNonNull`); семантические нарушения
  (валюта, знаки, диапазоны) — `IllegalArgumentException`. Эти два типа
  отказов не взаимозаменяемы.
- Все денежные параметры операции обязаны быть в валюте позиции (cash-операции
  — в переданной `currency`); нарушение → `IllegalArgumentException`.
- Знаковые проверки поименно: `requirePositive` (> 0) и `requireNonNegative`
  (≥ 0) на параметрах согласно перечню каждой операции ниже.
- **Optional-семантика налога**: в `coupon`/`amortization`/`sell`
  `taxWithheldTotal`/`taxOnGainTotal` — `Optional<Money>`; `Optional.empty()`
  эквивалентно нулю (налоговая проводка не создается). Напротив,
  `CouponReceiptService.confirm` (R10.6) принимает **три обязательных
   фактических суммы** (gross, tax, net). Ноль tax означает подтвержденное
   отсутствие удержания; неизвестное значение нельзя подменять нулем — до
   получения всех трех фактов подтверждение выплаты не выполняется.
- **Переполнение**: `buy` вычисляет `quantity' = Math.addExact(current
  .quantity(), quantity)` — переполнение `long` → `ArithmeticException`.
  Остальные денежные вычисления идут через `BigDecimal` (переполнение
  отсутствует по построению).
- **Нулевые entry опускаются**: проводка содержит только entry с ненулевой
  signed-суммой (правило `signed()`); базовый posting операции существует
  всегда (может содержать и ноль entry — тривиально сбалансирован; для
  cash-операций amount > 0, поэтому не встречается).
- Debit = положительная сумма, Credit = отрицательная (соглашение `Posting`,
  R8.17).
- OperationKind каждой операции и все инварианты `OperationResult`/
  `Posting`/`Commissions` — нормативно зафиксированы полностью в разделе 8.4
  (не «как раньше» — полный текст контрактов там).

**OPENING / DEPOSIT / WITHDRAWAL** (R8.9):

- amount обязана быть positive в переданной валюте.
- OPENING, DEPOSIT: `D cash[amount] / C equity[amount]`.
- WITHDRAWAL: `D equity[amount] / C cash[amount]`.
- Один posting; без position snapshots. Счета плоские (без security):
  `(portfolio, слот, empty, currency)`.

**BUY** (R8.10), settle-дата:

- Валидации: quantity > 0; cleanPricePerUnit ≥ 0; accruedPerUnit ≥ 0;
  facePerUnit > 0; компоненты commissions ≥ 0; все в валюте позиции;
  `current` может быть пустой позицией (покупка в ноль).
- `cleanTotal = cleanPricePerUnit × quantity` (точное `multiply(long)`,
  без округления); `accruedTotal = accruedPerUnit × quantity` (точно);
  `faceTotal = facePerUnit × quantity` (точно); `cashOut = cleanTotal +
  accruedTotal`.
- Позиция после: `quantity' = quantity + q` (addExact); `carrying' =
  carrying + cleanTotal`; `face' = face + faceTotal`; `purchasedAccrued' =
  purchasedAccrued + accruedTotal`.
- Базовый posting: `D securities[cleanTotal] / D accruedInterest[accruedTotal]
  / C cash[cashOut]` (нулевые entry опущены; securities/accruedInterest —
  securityScoped счета позиции, cash — плоский).
- Commission-posting (отдельный, только если `commissions.total() != 0`):
  `D commissionExpense[total] / C cash[total]`.
- Tax-posting: НЕ создается (buy всегда с tax = 0; нулевая проводка
  отсутствует — сохраняется).

**COUPON** (R8.11), payDate:

- Валидации: позиция открыта (quantity > 0); grossCouponTotal ≥ 0; tax ≥ 0;
  `tax ≤ grossCouponTotal`.
- `release = min(purchasedAccrued, grossCouponTotal)`; `income =
  grossCouponTotal − release`.
- Позиция после: количество/carrying/face без изменений;
  `purchasedAccrued' = purchasedAccrued − release`.
- Базовый posting: `D cash[grossCouponTotal] / C accruedInterest[release] /
  C couponIncome[income]`.
- Tax-posting (отдельный, если `tax != 0`): `D taxWithheld[tax] / C cash[tax]`.

**AMORTIZATION** (R8.12), payDate:

- Валидации: позиция открыта; faceReductionTotal > 0; paymentTotal ≥ 0;
  tax ≥ 0; `tax ≤ paymentTotal`; `faceReductionTotal ≤ faceAmount`;
  полное погашение (`faceReductionTotal == faceAmount`) требует
  `purchasedAccrued == 0`.
- `carryingRemoved` = при полном погашении — весь `carryingAmount`, иначе
  `proportional(carryingAmount, faceReductionTotal, faceAmount)`.
- `gain = paymentTotal − carryingRemoved` (может быть отрицательным — тогда
  credit с отрицательной суммой = debit по амортизации, правило signed).
- Позиция после: **количество не меняется** (в том числе при полном
  погашении номинала — quantity сохраняется; позиция с quantity > 0 и
  нулевыми суммами допустима по инвариантам R8.16, `Position.empty` не
  подставляется); `face' = face − faceReductionTotal`; `carrying' = carrying −
  carryingRemoved`; purchasedAccrued без изменений.
- Базовый posting: `D cash[paymentTotal] / C securities[carryingRemoved] /
  C amortizationGain[gain]` (сумма gain signed).
- Tax-posting: как в coupon, если `tax != 0`.

**SELL** (R8.13), settle-дата:

- Валидации: позиция открыта; quantity > 0; `quantity ≤ current.quantity()`;
  cleanPricePerUnit ≥ 0; accruedReceivedPerUnit ≥ 0; commissions ≥ 0; tax ≥ 0.
- `cleanValue = cleanPricePerUnit × quantity` (точно); `accruedReceived =
  accruedReceivedPerUnit × quantity` (точно).
- Полное выбытие (`quantity == current.quantity()`): `accruedRelease =
  purchasedAccrued` (весь); `carryingRemoved = carryingAmount`; `faceRemoved =
  faceAmount`. Иначе — пропорционально количеству:
  `accruedRelease = proportional(purchasedAccrued, q, Q)`;
  `carryingRemoved = proportional(carryingAmount, q, Q)`; `faceRemoved =
  proportional(faceAmount, q, Q)` (Q = текущее количество).
- `accruedIncome = accruedReceived − accruedRelease`; `realizedPnL =
  cleanValue − carryingRemoved`; `grossCash = cleanValue + accruedReceived`.
- Позиция после: при остатке 0 — `Position.empty(id, валюта)`; иначе остатки
  вычитаются.
- Базовый posting: `D cash[grossCash] / C securities[carryingRemoved] / C
  accruedInterest[accruedRelease] / C couponIncome[accruedIncome] / C
  realizedPnl[realizedPnL]` (accruedIncome и realizedPnL — signed, могут быть
  debit).
- Commission-posting и tax-posting — как в buy/coupon (при ненулевых
  комиссиях/удержании).

**TAX_CORRECTION** (R8.14):

- Валидации: `op != originalOperation`; `signedAdjustment != 0` (нулевая
  коррекция — `IllegalArgumentException`).
- Ровно один posting с `adjustsOperation = Optional.of(originalOperation)`
  и **двумя точно signed entry**:
  - entry по счету `taxWithheld` (плоский): amount = `signedAdjustment`
    (как есть, со знаком);
  - entry по счету `cash` (плоский): amount = `signedAdjustment.negate()`.
  Валюта обоих = валюта `signedAdjustment`.
- Примеры (валюта RUB):
  - увеличение удержания `signedAdjustment = +5.00`: taxWithheld **+5.00**,
    cash **−5.00** (дебет удержания, кредит денежных средств);
  - возврат `signedAdjustment = −3.00`: taxWithheld **−3.00**, cash
    **+3.00**.
- Без position snapshots. Семантика коррекции в ledger — раздел 10.

**`proportional` (R8.15)** — округление частичного списания:

```
scale = max(0, currency.defaultFractionDigits)
result = amount × numerator / denominator, HALF_UP, scale
if result > amount: result = amount   // защита от sub-minor-unit overdraft
отказ (IllegalArgumentException "Invalid proportional removal") если:
amount < 0, или denominator ≤ 0, или numerator < 0, или numerator > denominator
```

**Position-инварианты (R8.16)**: `Position` — record
`(PositionId id, long quantity, Money carryingAmount, Money faceAmount,
Money purchasedAccrued)`; одна валюта всех сумм (`IllegalArgumentException`
при нарушении); quantity ≥ 0; все sums ≥ 0; quantity == 0 ⇒ все суммы нулевые;
`Position.empty(id, currency)` — нулевая позиция. Quantity не является
измерением ledger-счета (N2); concurrency по количеству — stale-snapshot
проверкой (R7.6).

### 8.4. Полные контракты неизменяемых типов (нормативно)

Типы исключений нормативны; тексты сообщений — диагностика, не контракт
(R12.1). Null-дисциплина: `null`-компоненты → `NullPointerException`, всюду
отдельно от `IllegalArgumentException`.

**R8.17 — `Posting`** (record `(OperationId operation, LocalDate date,
List<Entry> entries, Optional<OperationId> adjustsOperation)`; convenience-
конструктор без adjustsOperation приравнивает его к `Optional.empty()`):

- entries defensively-копируются (`List.copyOf`); null-элементы → NPE.
- `adjustsOperation` обязан быть non-null Optional; posting не может
  корректировать собственную операцию (`operation.equals(adjustsOperation)`
  → `IllegalArgumentException`).
- Баланс: сумма entry-amounts по каждой валюте обязана быть нулевой;
  ненулевой итог → `UnbalancedPostingException` (подтип
  `IllegalArgumentException`).
- `Entry` (record `(Account account, Money amount)`): валюта amount обязана
  равняться валюте account → иначе `IllegalArgumentException`.
- Положительная сумма = debit, отрицательная = credit.

**R8.18 — `OperationResult`** (final class; package-private конструктор,
сцепленный с `BondOperations` — сохраняется; enum `OperationKind`:
OPENING, DEPOSIT, WITHDRAWAL, PURCHASE, COUPON, AMORTIZATION, SALE,
TAX_CORRECTION). Конструктор валидирует (всё — `IllegalArgumentException`,
кроме NPE):

- postings — непустая защитная копия;
- каждый posting: operation и date совпадают с result;
- для каждого posting: `(kind == TAX_CORRECTION) ==
  posting.adjustsOperation().isPresent()` — только налоговые коррекции могут
  ссылаться на скорректированную операцию, и обязаны;
- `kind == TAX_CORRECTION` ⇒ ровно один posting;
- security-операции := PURCHASE, COUPON, AMORTIZATION, SALE: presence
  `positionBefore`/`positionAfter` обязана совпадать с security-классификацией
  вида (обе присутствуют для security-операций; обе отсутствуют для
  OPENING/DEPOSIT/WITHDRAWAL/TAX_CORRECTION);
- security-операции: `before.id() == after.id()` и одинаковая валюта
  carryingAmount.

**R8.19 — `Commissions`** (record `(Money brokerCommission, Money
otherCommission)`): одна валюта компонентов; оба компонента неотрицательны;
`total() = brokerCommission.add(otherCommission)`. Money-overload-ы
`buy`/`sell` строят `Commissions(commission, Money.zero(currency))`.

**R8.20 — `CouponReceipt`** (application-слой, record
`(InvestmentAccount account, PositionId position, OperationId operation,
LocalDate actualDate, Money grossTotal, Money taxWithheldTotal, Money
netReceivedTotal, LedgerSnapshot ledgerSnapshot)`): портфели account/
position/ledgerSnapshot совпадают; все три суммы неотрицательны, в одной
валюте, `gross == tax + net`; `actualDate` не ранее IIS-3 `openingDate`
(при наличии); операция присутствует в `ledgerSnapshot.state().
operationIds()`. Все нарушения — `IllegalArgumentException` (NPE для null).

## 9. `restore` — структурная валидация (не достижимость)

- R9.1 — `Ledger.restore(state)` валидирует и восстанавливает состояние;
  сигнатура не меняется; chart берется из state (R6.5).
- R9.2 — restore проверяет **структурную согласованность** (полный
  нормативный перечень, chart-параметризованный):
  - балансы: portfolio-скопинг; валюта баланса == валюта счета; нулевые
    остатки отсутствуют; noNegative при строгой политике;
  - **R9.3 (covering)**: каждый `Account.code` в balances и в каждом entry
    истории ∈ `chart.knownCodes` — иначе
    `IllegalArgumentException("Invalid ledger state: …")`; включая R7.7
    scoping-правило по chart;
  - позиции: ключ == identity, portfolio-скопинг;
  - история: непустые date-buckets; дата posting == bucket; один operationId
    не встречается в нескольких датах; replay суммы == balances (zero-
    omission);
  - `operationIds == множество операций истории`;
  - adjustment-история (раздел 10.3) и position bindings (R7.9).
- R9.4 — restore **НЕ доказывает историческую достижимость** состояния (нет
  доказательства существования последовательности операций, породившей
  историю); это утверждение сохраняется из текущего контракта и не меняется.
- R9.5 — `LedgerSnapshot` (application-порт) не меняется: его ctor
  `Ledger.restore(state)` работает через самодостаточный state.
- R9.6 — `OperationResult` и `OperationRecord` не меняются: `OperationKind`
  enum, все проверки конструкторов — нормативно зафиксированы в R8.18 (и для
  `OperationRecord`: kind/operation/date/postings-identity, sequence > 0,
  непустые postings, соответствие snapshots виду операции). Диспетчеризация
  adjustment в `Ledger.apply` остается enum-based (`kind ==
  TAX_CORRECTION`, R7.5) — предлагаемая граница scope (раздел 1, N6):
  dehardcode охватывает словарь счетов, не таксономию операций.

## 10. Adjustments (налоговые корректировки) и CAS

### 10.1. Инварианты adjustment (сохраняются полностью)

- Append-only: коррекция — новая операция; исходная история, позиции, доход и
  PnL не переписываются.
- Связь: `Posting.adjustsOperation()` → исходная операция. Correction-to-
  correction запрещена (как в `validateTaxCorrectionHistory`: adjustsOperation
  не может указывать на операцию, имеющую собственный link).
- Хронология: дата коррекции ≥ даты исходной операции; исходная операция уже
  существует в ledger.
- Валюта коррекции == валюте накопленного удержания исходной операции.
- Накопленное удержание после коррекции ≥ 0.

### 10.2. Валидация в `apply` (R10.1)

При диспетчеризации `kind == TAX_CORRECTION` (R7.5):

1. `adjustsOperation` присутствует (гарантировано ctor `OperationResult`).
2. Исходная операция ∈ `operationIds` → иначе
   `IllegalStateException("Tax correction references an unknown operation…")`.
3. Дата коррекции ≥ даты исходной (по истории) → иначе
   `IllegalStateException("Tax correction precedes…")`.
4. Форма transfer-пары по chart: ровно два entry; один по счету с кодом
   `chart.adjustableCode()` (плоский), один по счету с кодом
   `chart.adjustmentCounterpartCode()` (плоский); равные противоположные суммы
   в одной валюте; оба счета портфеля. Нарушение — `IllegalArgumentException`
   из валидатора пары, оборачиваемый `apply` в `IllegalStateException`
   (обертка — нормативна: apply-контекст, см. §12).
5. Ненулевая сумма (zero-коррекция отклоняется).
6. `current = taxWithheldForOperation(original)`; валюты совпадают;
   `current + adjustment ≥ 0` → иначе `IllegalStateException`.

### 10.3. Валидация истории в restore (R10.3)

Restore валидирует историю adjustment-ов (полный нормативный перечень,
код-параметризованный по chart):

1. каждая операция, имеющая posting с `adjustsOperation`, содержит **ровно
   один** posting и не является исходной withholding-операцией;
2. каждый posting с `adjustsOperation` проходит форму transfer-пары
   (подтверждение п.4 R10.1) и имеет ненулевую сумму;
3. исходные withholding-posting-и (entry по коду `adjustableCode` без link):
   без `adjustsOperation`, форма пары, **положительная** сумма; не более
   одного исходного на операцию (несколько → нарушение структурной
   согласованности);
4. каждая коррекция ссылается на операцию, имеющую исходный
   withholding-posting **раньше по истории** (в хронологическом порядке
   бакетов), и не на другую коррекцию;
5. валюта коррекции == валюте исходного удержания;
6. накопленное удержание каждой исходной операции ≥ 0 **после каждой**
   коррекции в хронологии (нарушение — нарушение структурной
   согласованности, `IllegalArgumentException`-обертка restore, §12).

## 11. Порты и in-memory репозиторий

### 11.1. Неизменяемые порты

- R11.1 — `LedgerRepository`, `LedgerJournal`, `LedgerSnapshot`,
  `OperationRecord`, `DuplicateOperationException`,
  `LedgerConcurrencyException`, `RepositoryConfig`,
  `LedgerRepositoryFactory.create(RepositoryConfig)` — не меняются.

### 11.2. `LedgerCommit`

- Канонический конструктор: `LedgerCommit(long expectedVersion, LedgerState before,
  OperationResult operation, LedgerState after)`. Все объектные компоненты обязательны.
  `expectedVersion >= 0`; портфель и cash-policy before/after совпадают;
  при version 0 before пуст по R6.6; при version > 0 before содержит операции.
  Нарушения — `IllegalArgumentException`. Уже присутствующий в before operation ID
  отклоняется `DuplicateOperationException`. Вычисляется
  `Ledger.restore(before).apply(operation)`; результат обязан точно равняться after,
  иначе `IllegalArgumentException`. `portfolio()` возвращает `before.portfolio()`.

- R11.2 — shape не меняется; ctor-валидации сохраняются, плюс одна явная
  проверка: `before.chart().equals(after.chart())` — иначе
  `IllegalArgumentException("Commit cannot change portfolio, chart, or
  negative-cash policy")` (расширение существующей строки 19–21; chart-
  равенство и так следует из `restore(before).apply(operation).state().
  equals(after)`, но проверяется явно для симметрии и раннего отказа).
  Существующая re-валидация `Ledger.restore(before).apply(operation)` в ctor
  работает через самодостаточный state без изменения кода.

### 11.3. `InMemoryLedgerRepository`

- R11.3 — единственное изменение: строка 79 (`Ledger.open(commit.portfolio(),
  commit.before().allowNegativeCash())`) → `Ledger.open(commit.portfolio(),
  commit.before().chart(), commit.before().allowNegativeCash())`. Реконструкция
  пустого before для первой записи берет chart из самого `commit.before()`.
- R11.4 — **начальная запись (version 0) выбирает chart, без гарантии
  подлинности**: `LedgerCommit` требует пустой before (R6.6); репозиторий
  реконструирует `Ledger.open(portfolio, before.chart(), before.
  allowNegativeCash())` и сравнивает на точное равенство с `commit.before()`.
  Реконструкция берет chart из самого `commit.before()` — **независимого
  доверенного источника chart не существует**, поэтому «подмена» chart при
  первом commit **не детектируется**: любой валидный chart, поданный в
  корректном пустом before, принимается. Первый успешный commit фиксирует
  chart портфеля (TR2); при конкурентных первых записях с разными policy
  CAS арбитрирует — побеждает одна, остальные получают
  `LedgerConcurrencyException` (DE-N-09). Гарантия для **последующих**
  записей сохраняется: CAS-сравнение состояний включает chart (R6.4), и
  точное before-равенство отклоняет любую запись с другим chart.
- R11.5 — re-валидация `commit:88` (`Ledger.restore(actualBefore).
  apply(commit.operation())` + сравнение after) и `validateJournal:135`
  работают без изменений (самодостаточный state).
- R11.6 — провайдер `memory`, `RepositoryConfig` без настроек, изоляция
  реестров, per-portfolio блокировка, полная история — без изменений.

## 12. Taxonomy отказов

Null-дисциплина всюду: `null`-аргументы/компоненты → `NullPointerException`;
они не перечислены в таблице по строкам и никогда не отображаются в
`IllegalArgumentException`.

| Ситуация | Исключение | Место |
|---|---|---|
| Неверный формат кода; аргументы операций (валюта, знаки, диапазоны); неизвестный/непокрытый код в state; неверная covering/scoping в restore; malformed adjustment posting; zero-delta коррекции; запрос баланса неизвестного кода/scoping-нарушение (R7.15) | `IllegalArgumentException` (в т.ч. `UnbalancedPostingException`) | конструкторы типов; restore; сервисы |
| Duplicate OperationId; backdated; stale position snapshot; позиция другого портфеля; unknown account code в проводке (R7.7); insufficient funds (noNegative); несоответствие position bindings; коррекция без исходной/раньше исходной; отрицательное накопленное удержание | `IllegalStateException` | `Ledger.apply`; `Ledger.restore` (обертывается в `IllegalArgumentException "Invalid ledger state: …"`); сервисы |
| Конфликт CAS (версия/точный before) | `LedgerConcurrencyException` (application) | `commit` |
| Дубликат операции в commit | `DuplicateOperationException` (application) | `commit`, сервисы |
| Chart/policy дрейф (state.chart != policy.chart) | `IllegalStateException` | `LedgerApplicationService.apply`, `TaxCorrectionService.correct` |
| Несовпадение cash-policy | `IllegalStateException` | сервисы |
| Переполнение `long` количества (buy) | `ArithmeticException` | `BondOperations.buy` (R8.8) |

R12.1 — **типы исключений нормативны; тексты сообщений — диагностика, не
контракт**. Реализация обязана сохранять типы и условия отказа, перечисленные
здесь и в R5–R11; конкретные тексты могут отличаться от текущих и не
проверяются тестами как контракт (тесты утверждают тип и условия, при
необходимости — устойчивые подстроки-маркеры, зафиксированные в самой
спецификации, например `"Invalid ledger state"`-префикс restore-обертки).

- DE-N-02 AccountCode формат (R5.1).
- DE-N-03 apply: **unknown код в entry → `IllegalStateException`** (явный
  guard, никогда не «молчаливый ноль»); security present у non-scoped кода и

- DE-N-04 apply: noNegative **per-account, не агрегат** — один счет

- DE-N-05 adjustment: неизвестная исходная операция; раньше даты исходной;

## 14. Совместимость и breaking-изменения (целевое предложение)

**Ломаются (полный перечень; source- и binary-incompatible):**

1. `AccountKind` — enum удаляется; замена: `AccountCode` + слоты
   `BondAccountingPolicy`.
2. `Account` — компонент `kind` заменяется на `code` типа `AccountCode`;
   accessor `kind()` заменяется на `code()`, конструктор и equality меняются.
3. `LedgerState` — новый компонент `chart` (вторая позиция); канонический
   конструктор и equality меняются.
4. `BondOperations` — все static-методы удаляются (без фасада); замена —
   instance, сконфигурированный policy (R8.5).
5. `Ledger.open(PortfolioId)` и `Ledger.open(PortfolioId, boolean)` —
   удаляются; единственная фабрика `open(PortfolioId, LedgerChart, boolean)`.
6. Конструкторы сервисов ломаются: `LedgerApplicationService(repository)` →
   `(repository, policy)`; `TaxCorrectionService(repository)` →
   `(repository, policy)`; `CouponReceiptService(accounts, ledgers)` →
   `(accounts, ledgers, policy)`.

**Не меняются (shape/API/поведение):** `Posting`, `Entry`, `OperationResult`,
`OperationKind`, `Commissions`, `Position`, `UnbalancedPostingException`,
`LedgerSnapshot` (включая ctor-валидацию через `Ledger.restore(state)`),
`OperationRecord`, `LedgerRepository`, `LedgerJournal`,
`LedgerCommit` (shape; добавляется одна проверка R11.2), `RepositoryConfig`,
`LedgerRepositoryFactory`, все `module-info.java`, провайдеры ServiceLoader,
`Main` (сервисы учета в нем сегодня не создаются; при будущей сборке
composition root обязан создавать ровно один `BondAccountingPolicy` и
передавать во все сервисы — R8.3, фиксируется в AGENTS).

Отсутствие deprecated-фасада — целевое предложение AD-2. Его обоснование
опирается на **A1 (предположение, не доказанный факт**: JPMS не доказывает
отсутствие внешних потребителей — требуется явное подтверждение пользователя)
и A2 (in-memory persistence, persisted-данных нет); правила репо требуют
явности, скрытые дефолты запрещены. До подтверждения A1 любое из перечисленных
удалений может быть переоценено новой версией спецификации.

## 16. Порядок миграции

- **Подготовка (независимо поставляема, до change-set, старая архитектура):**
  characterization-дополнения `LedgerContractTests` (поведение, зависящее от
  ролей: negative-policy, views, correction-механика) — фиксация текущего
   поведения. Измененные тесты запускаются целевым Gradle task; только
   документационные изменения без изменения тестов запуска Gradle не требуют.
- **Целевой change-set — один, неделимый на поставки** (один merge/ревью):
  все новые типы + все изменения `core`, `application`, `persistence-memory`
  (разделы 5–12, 15) + миграция тестов 13.1 + новая матрица 13.2 (включая
  DE-P-14 end-to-end custom-словарь) + guard-расширения + документация/
  AGENTS — **вместе**. Промежуточное состояние «core изменен, application
  нет» не компилируется (static `BondOperations` удален) — поэтому подшаги
  внутри change-set являются **только порядтом работ** (core → application →
  memory → tests → docs), а не отдельными поставками; никакая поставка
  (merge/release) новой архитектуры без одновременных docs/guards/tests
  недопустима.
- **Финальная проверка — один полный прогон** в конце change-set:
  `./gradlew clean build` + `jacocoAggregateReport` + root
  `ModulePathContractTests`. На подшагах допускаются частичные прогоны
  затронутых модулей (`:core:check` и т.п.) как рабочий инструмент; полный
  suite повторяется на каждый подшаг **не** обязателен.
- Версия получает статус IMPLEMENTED в индексе README только после зеленого
  финального прогона (evidence — в индексе).

## 19. Решения, требующие утверждения (НЕ одобрены)

Спецификация предлагает конкретные решения; до утверждения статус остается
DRAFT и каждое из них может изменить содержимое новой версией.

- **AD-1 Имя типа кода**: `AccountCode` (record со строковым `value`).
  Альтернатива, отвергнутая: сохранить имя `AccountKind` за value-классом
  (меньше doc-churn, но двусмысленно со старым enum).
- **AD-2 Breaking без фасада**: полный перечень раздела 14 (enum
  `AccountKind`, типы полей `Account`/`LedgerState`, static `BondOperations`,
  overload-ы `Ledger.open`, конструкторы трех сервисов) без deprecated-моста.
  Альтернатива, отвергнутая: deprecated-фасад на один релиз — скрывает
  источник словаря и противоречит принципу явности репо. Обоснование опирается
  на **A1 — неподтвержденное предположение** об отсутствии внешних
  потребителей (JPMS этого не доказывает); до подтверждения A1 решение
  может быть переоценено.
- **AD-3 Заморозка chart при open**: chart — часть идентичности ledger
  (R6.7/R6.8); mid-life смена запрещена; миграция chart — отдельная будущая
  спецификация. Первый commit выбирает chart без гарантии подлинности
  (R11.4, TR2).
- **AD-4 Множественность spendable/noNegative ролей**: разрешены (R5.6,
  R5.8; агрегация view и per-account запрет определены для множеств),
  стандартный chart использует по одному коду; adjustable — ровно один
  (скалярный параметр API); alias position-bindings запрещены (R5.7).
  Альтернатива: запрет множественности всех ролей в v1 (строже, но без
  потребности).
- **AD-5 Пассивные известные коды**: поддерживаются (R5.8) — «лишние» плоские
  счета без ролей допустимы; явного отказа нет. Альтернатива: требовать роль
  для каждого кода (не нужно: EQUITY/COUPON_INCOME/… пассивны).
- **AD-6 `OperationKind` остается enum-контрактом, включая enum-диспетчеризацию
   `TAX_CORRECTION` в `Ledger.apply`** (раздел 1, N6, R7.5, R9.6) — предлагаемая
   граница scope: таксономия операций не переводится в данные; запрос
  касался плана счетов.
- **AD-7 Сохранение имен tax-view API**: `cashBalances()`/
  `taxWithheldBalances()`/`taxWithheldForOperation()` остаются на `Ledger`
  (реализация через роли), а не переименовываются в нейтральные
  `adjustmentTotalFor(...)` (меньше рябь в application/тестах/AGENTS;
  bond-семантика имен признана приемлемой).
- **AD-8 Изменение семантики `Ledger.balance()`** (R7.15): неизвестный chart-у
  код и scoping-нарушение отклоняются `IllegalArgumentException` вместо
  молчаливого нуля текущей реализации; известный корректный несуществующий
  счет возвращает zero. Совместимость меняется явно (тест DE-N-11);
  альтернатива — сохранить «ноль для всего» — отвергнута: молчаливый ноль
  маскирует конфигурационные ошибки.
- **AD-9 Тексты исключений — диагностика, не контракт** (R12.1): нормативны
  типы и условия отказа; реализация не обязана воспроизводить текущие
  строки. Альтернатива, отвергнутая: полный message catalog — хрупкость без
  потребности.
