# Лимиты ответов MOEX и CBR — исследование 21 октября 2026

Основание: [ревью проекта](2026-10-21-project-review.md), раздел безопасности.
Исследованы только запросы, которые выполняют текущие адаптеры, а не API целиком.
Приведенные ниже бюджеты внедрены в транспорт и XML-адаптеры. Новых внешних
зависимостей нет: используются JDK 25 `java.net.http` и `java.xml`.

## Метод и границы достоверности

Измерения выполнены на публичных API с явно отключенным прокси:

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
    -u http_proxy -u https_proxy -u all_proxy -u NO_PROXY -u no_proxy \
    curl --noproxy '*' --connect-timeout 10 --max-time 40 "$URL"
```

Числа относятся к байтам тела без HTTP-заголовков и framing, без сжатия.
Текущие адаптеры не запрашивают gzip; при добавлении распаковки нужен дополнительный
лимит распакованных данных. `Content-Length` не заменяет счетчик фактически полученных байтов.
На HTTP MOEX наблюдался chunked transfer без `Content-Length`.

Это выборочные наблюдения на указанную дату, не доказательство максимального размера,
полноты выдачи или отсутствия серверного усечения. Нет документированного верхнего
предела сериализованного ответа для используемых методов. Настраиваемый защитный бюджет
может отвергнуть будущий легитимный ответ; такое событие должно быть явной ошибкой.

Рабочие образцы и подробные протоколы: `.opencode/tmp/moex-research/` и
`.opencode/tmp/cbr-research/`; это локальные исследовательские артефакты, не тестовые зависимости.

## MOEX ISS

Запросы адаптера:

- `/iss/securities/{SECID}.xml?iss.meta=off&iss.only=description`;
- `/iss/securities/{SECID}/bondization.xml?iss.meta=off&iss.only={block}&limit=20&start={offset}`,
  где `block` — `coupons`, `amortizations` или `offers`.

В выборке были фиксированные и плавающие ОФЗ, амортизируемые выпуски, длинные
расписания до 2062/2074 года и выпуски разных эмитентов.

| Блок | Наибольшее измеренное тело, байт | Строк в этом ответе | Атрибутов в строке |
|---|---:|---:|---:|
| description | 7 637 | 45 | 7 |
| coupons | 32 723 | 100 | 14 |
| amortizations | 29 683 | 100 | 13 |
| offers | 4 335 | 13 | 14 |

Страницы на 100 строк запрошены отдельно для исследования запаса; текущий адаптер
запрашивает 20. При `limit=101/200/500/1000/2000` на двух длинных расписаниях
наблюдались 100 строк. Это наблюдаемый cap, а не документированная гарантия bondization.
Описание возвращалось целиком, без пагинации. Глубина XML используемых ответов — 4.

Неизвестный SECID, пустое расписание и смещение за концом возвращают HTTP 200 с пустыми
`rows`. Неизвестный блок или путь может вернуть HTTP 200 с другим набором блоков:
проверка ожидаемого блока обязательна, HTTP-статуса недостаточно. Ответы 5xx в этой
выборке не получены; отдельный размер типичной страницы сбоя не установлен.

В метаданных MOEX для `description.value` указана ширина 6144, для `title` — 765.
Это не верхняя граница тела XML: необходимы учет единиц ширины, UTF-8, экранирования,
числа строк и остальных полей. Нельзя выводить гарантированный byte cap простой суммой
этих значений и наблюдаемых 45 строк.

HTTP и HTTPS на точных путях адаптера дали 200, без редиректов, с одинаковыми телами.
HTTPS работал напрямую с проверкой сертификата. Выбор HTTP по умолчанию отдельно
подтвержден пользователем: это отказ от TLS, а не обход неисправности HTTPS.

## CBR DailyInfoWebServ

Адаптер выполняет SOAP 1.1 POST на
`https://www.cbr.ru/DailyInfoWebServ/DailyInfo.asmx`:

- `KeyRateXML(fromDate, ToDate)` для `RU_KEY_RATE`;
- `RuoniaXML(fromDate, ToDate)` для `RUONIA`.

| Метод | Наибольшее измеренное тело, байт | Записей | Глубина | Наибольший текст, символов |
|---|---:|---:|---:|---:|
| KeyRateXML | 198 864 | 3 284 | 7 | 25 |
| RuoniaXML | 446 254 | 4 133 | 7 | 29 |

Измерены широкие исторические диапазоны. Отсутствие добавочных строк при более ранней
начальной дате не доказывает полноту истории или независимость ответа от диапазона.
WSDL не задает byte/record cap; опубликованные схемы допускают неограниченную кратность.

Наблюдавшиеся варианты:

- HTTP 200 с inline XML внутри SOAP result;
- HTTP 200 с пустым корневым элементом данных, около 371–382 байт;
- HTTP 200 с `<Error/>` при некорректном запросе: нельзя считать отсутствующим fixing;
- HTTP 500 с HTML, около 10,7 KB, а не SOAP Fault.

SOAP Fault и escaped XML внутри result поддерживаются текущим кодом/фикстурами,
но не наблюдались в этих live-ответах. Повторный разбор вложенного XML должен получать
тот же защитный профиль. Связанная XSD ключевой ставки описывает `Item`, а измеренный
метод возвращает `KR`; нельзя объявлять эту XSD точной схемой текущего ответа.

## Действующие начальные бюджеты

| Ограничение | MOEX | CBR |
|---|---:|---:|
| Байты одного ответа, включая HTTP-ошибки | **512 KiB** | **2 MiB** |
| Глубина XML | **8** | **32** |
| Атрибутов на элемент | **32** | **16** |
| Длина значения атрибута после XML-декодирования | **8192 символа** | **1024 символа** |
| Длина текстового поля после XML-декодирования | **1024 символа** | **1024 символа** |
| Строк в одном ответе | description **256**, страница расписания **128** | **20 000** |

512 KiB дает примерно 16-кратный запас к крупнейшему измеренному MOEX-ответу,
2 MiB — примерно 4,7-кратный к CBR. Это практические бюджеты с запасом, не математически
оптимальные или гарантированно достаточные значения. Рост данных и изменение API
потребуют пересмотра. Для MOEX существующие общие пределы 1000 страниц / 20 000 строк
на блок пока сохранить: сужать их по небольшой выборке выпусков недостаточно обоснованно.

Лимиты принадлежат конкретному провайдеру; общий `HttpTransport` не требует одинаковых
чисел для MOEX и CBR. Профиль передается в экземпляры транспорта и XML helper,
без расширения provider SPI. Все новые настройки — положительные целые числа;
некорректные, нулевые, отрицательные и переполняющие тип значения отклоняются до запроса.

| Настройка MOEX | Настройка CBR | Смысл |
|---|---|---|
| `moex.maxResponseBytes` | `max-response-bytes` | Байты тела |
| `moex.maxXmlDepth` | `max-xml-depth` | Глубина XML |
| `moex.maxXmlAttributes` | `max-xml-attributes` | Атрибуты на элемент |
| `moex.maxXmlAttributeLength` | `max-xml-attribute-length` | Длина значения атрибута |
| `moex.maxXmlTextLength` | `max-xml-text-length` | Суммарный прямой текст и CDATA элемента |
| `moex.maxDescriptionRows` | — | Строки описания |
| `moex.maxPageRows` | — | Строки страницы расписания |
| — | `max-series-rows` | Записи серии |

Длины Java-строк считаются в UTF-16 code units после XML-декодирования, не в байтах.
SOAP-контейнер CBR с escaped XML может содержать текст длиннее лимита отдельного поля:
для внешнего конверта он ограничен бюджетом тела, а извлеченные данные повторно
проверяются строгим XML-профилем. Ограничение полей не обходится разбиением на CDATA.

## Реализация и проверки

- HTTP: JDK 25 `BodyHandlers.limiting(...)`, прекращение чтения при превышении,
  включая неуспешные HTTP-статусы. Неизвестные Content-Encoding отклоняются;
  их тела также не могут обойти byte cap. Автоматическая распаковка не добавлена.
- XML: per-factory `jdk.xml.maxElementDepth`, `jdk.xml.elementAttributeLimit`, текущие
  запреты DTD/XXE; итеративный обход вместо рекурсии.
- Ограничения текста/значений атрибутов и числа записей проверяются отдельно:
  JAXP depth/attribute-count properties их не заменяют. Проверка после построения DOM
  защищает дальнейшую обработку, но не предотвращает уже понесенные расходы DOM;
  предварительный byte cap остается обязательным. Для ранних структурных отказов можно
  отдельно оценить потоковый SAX/StAX, не вводя его автоматически ради этой задачи.
- XML namespace declarations учитывались как атрибуты при измерениях. Отдельный probe
  установленного JDK 25 подтвердил: `elementAttributeLimit=1` отвергает как два обычных
  атрибута, так и две namespace declarations.
- Превышение любого лимита — отказ всего результата, не усечение и не «нет fixing».
- Офлайн-тесты проверяют ровно предел / превышение, ошибочные ответы, глубокий XML,
  вложенный XML CBR и ограничение записей до накопления списка. Cumulative byte cap
  и отмена подписки проверяются настоящим JDK BodySubscriber с fake HttpClient,
  подающим несколько порций без Content-Length; это не live-тест HTTP chunked framing.
  Fake `Transport` обходит HTTP-защиту, поэтому адаптеры дополнительно проверяют
  размер UTF-8 строки перед разбором. Новые проверки не обращаются к внешним API.

Проверка внедрения: `./gradlew --offline build` на JDK 25 с отключенными
proxy-переменными завершилась успешно: 115 тестов без ошибок и пропусков,
включая root module-path/distribution suite. Native Image не собирался;
новые зависимости и изменения JPMS descriptors не потребовались.
